# SPEC.md — функциональные требования

Формулы и константы — в `docs/DOMAIN.md`. Здесь только «что видит и делает пользователь».

---

## 1. Сценарий использования

Промышленник в EVE Online собирается закупить партию газа для реакций. Газ торгуется в
двух формах — сырой (объёмный, годен для производства сразу) и сжатый (в 10 раз компактнее,
но перед использованием теряет 5–20% при разжатии). Дешевле возить сжатый, но купить
придётся больше. Цены и глубина стакана в пяти хабах разные, стоимость доставки из каждого
хаба тоже разная.

Пользователь открывает страницу, выбирает газ, вводит параметры, видит **одну таблицу**
и понимает, куда лететь сегодня. Всё.

## 2. Одна страница, три блока

```
┌─────────────────────────────────────────┐
│  Блок 1. Параметры расчёта              │
├─────────────────────────────────────────┤
│  Блок 2. Сетка цен 5×4                  │
├─────────────────────────────────────────┤
│  Блок 3. Результат: сводка + таблица    │
└─────────────────────────────────────────┘
```

Пересчёт — автоматический при изменении любого поля (через HTMX, с debounce);
кнопка «Посчитать» тоже работает и остаётся для тех, кому так привычнее.

## 3. Блок 1 — параметры

| Поле | Тип | По умолчанию | Валидация |
|------|-----|--------------|-----------|
| Газ | select, все типы из `data/gases.json`, сгруппированы по семействам | Fullerite-C320 | обязательно |
| Нужно юнитов сырого | int | 10000 | > 0 |
| Тип структуры | select: Upwell / Athanor / Tatara | Athanor | — |
| Навык Gas Decompression Efficiency | select 0..5 | 5 | 0..5 |
| Брокерская комиссия, % | float | 1.5 | 0..5 |
| Обеспечение, % от стоимости газа | float | 0.5 | 0..100 |

Рядом с полем структуры и навыка — **живой вывод итоговой эффективности**: «Разжатие: 89%».
Пользователь должен видеть, что он настроил, не открывая справочник.

Под селектом газа — объёмы выбранного типа: «5 м³ сырой / 0.5 м³ сжатый».

## 4. Блок 2 — сетка цен

Таблица 5 строк × 5 колонок. Строки — хабы в порядке из `DOMAIN.md`.

| Хаб | Доставка, ISK/м³ | Сырой sell | Сырой buy | Сжатый sell | Сжатый buy |
|-----|------------------|------------|-----------|-------------|------------|
| Jita | [input] | [input] | [input] | [input] | [input] |
| Amarr | [input] | [input] | [input] | [input] | [input] |
| ... | | | | | |

**Все ячейки заполняются вручную.** Это основной режим ввода. Ставка доставки своя
у каждого хаба — это отдельная колонка, не общее поле.

Поведение при незаполненных ячейках:

- Пустая цена → соответствующий сценарий **не попадает** в результирующую таблицу. Не ноль, не ошибка — просто отсутствует.
- Пустая ставка доставки → все четыре сценария этого хаба выпадают, строка помечается как «не задана доставка».
- Заполнена хотя бы одна ячейка → расчёт возможен.

Цены подставляются **из базы** при открытии страницы и при смене газа, количества,
структуры или навыка: средневзвешенная зависит от нужного объёма, а он меняется
вместе с этими полями. Подставленные значения показаны приглушённо и перебиваются
вводом — ручной ввод всегда главнее, и такую ячейку сервер больше не трогает.

Кнопки подтяжки нет и быть не может: пользователь не инициирует обращений к ESI
ни при каких условиях. Цены собирает задача по расписанию (`app/jobs/collect.py`).

Под сеткой пишется только то, что пошло не так: недоступная база, ещё не собранные
цены, устаревшие данные, хабы без среза, книга целиком вне рынка, незаполненный
`type_id`. В обычный день там пусто — рассказывать, что всё хорошо, незачем:
это видно по самим ценам, а возраст данных стоит чипом в шапке.

Молчать про эти случаи по-прежнему нельзя: недоступная база, пустая база и хаб
без среза выглядят на экране одинаково — пустой ячейкой, и отличить их человеку
иначе не по чему. Пояснения о том, как работает сетка («пустая ячейка — сценарий
не участвует», оговорка про радиус buy-ордеров), убраны 22.08.2026 вместе
с остальным поясняющим текстом.

Ручной ввод — мастер. База — черновик.

## 5. Блок 3 — результат

### 5.1 Сводка

Три числа крупно:

- **Лучший вариант** — ISK за полезный юнит + подпись «Amarr, сжатый, buy».
- **Разница с худшим** — сколько ISK экономит лучший вариант на всей партии.
- **Потери при разжатии** — сколько юнитов сгорит и сколько это процентов. Показывать только если в выдаче есть сжатые сценарии.

### 5.2 Основная таблица

Колонки:

| Колонка | Содержимое |
|---------|------------|
| Хаб | название |
| Что берём | «сжатый · buy» и т.п. |
| Цена | цена за юнит, как введена |
| 7 дней | спарклайн: форма движения дневных средних цен сделок за неделю. Прочерк, если линию строить не из чего |
| Сделки | опорная цена реальных сделок за неделю, под ней мелким — диапазон `min … max`. Если в этом регионе газом не торговали — цифры соседних хабов с пометкой «по другим хабам». Прочерк, если истории нет нигде |
| Продано | среднесуточный оборот этого типа в регионе хаба. Прочерк, если опора заимствована: чужой оборот за свой не выдаётся |
| Купить | сколько юнитов покупаем (для сжатого — с запасом на потери) |
| Объём | м³ груза |
| Доставка | ISK: объём × ставка плюс надбавка за обеспечение |
| Итого | ISK |
| ISK/юнит | **главная колонка**, по ней сортировка по возрастанию |
| Δ | отставание от лучшего варианта в процентах, у первой строки прочерк |

Первая строка выделена. Строки с предупреждениями помечены.

Колонка **«7 дней»** — та же история, но формой, а не числом: видно, стоит ли цена
на месте или неделю ползёт в одну сторону. Уровень намеренно не показывается,
линия нормируется по собственному размаху — абсолютные числа стоят рядом
в «Сделках», и дублировать их графиком незачем.

Цвет линии — **по интересу покупателя, а не по направлению**: дешевеющий газ
зелёный, дорожающий красный. В макете цвета стоят наоборот; макет — источник
вёрстки и палитры, но не источник смысла. Движение меньше 2 % за неделю
не называется движением вовсе и рисуется нейтральным цветом: недельный шум —
не тренд. Точное изменение и число дней — в подсказке.

Линии нет в двух случаях, и подсказка их различает: в истории меньше двух дней
с реальными сделками, либо свод заимствован у соседних хабов — чужое движение
выдавать за движение этого хаба нельзя. История регионная и стороны не разделяет
(`ESI.md` §5.2), поэтому у строк `sell` и `buy` одного хаба линия одна и та же.

Колонки «Сделки» и «Продано» отвечают на один вопрос: правда ли по этой цене торгуют
и можно ли по ней набрать нужный объём. Числа берутся из истории сделок ESI,
считаются по `docs/ESI.md` §5.5 и показываются одинаково для цен из базы и введённых
руками. Если истории по паре «хаб + форма» нет — в обеих колонках прочерк, и это
не ошибка.

### 5.3 Точки безубыточности

Живут в разборе строки (§5.8): у каждого хаба своя, и стоит она рядом с ценами
этого же хаба.

> В Jita сжатый выгоднее сырого, пока стоит дешевле **4 645 ISK**

Считается по формуле из `DOMAIN.md` — по ценам sell, поэтому фильтрам сторон
(§5.4) не подчиняется: точка видна и когда в таблице одни buy-строки. Если одной
из цен sell по хабу нет, показывается не пустое место, а какой именно цены
не хватает.

До 22.08.2026 это был отдельный блок под таблицей со строкой на каждый хаб.
Блок убран по решению пользователя — как и нарисовано в макете. Цена вопроса
названа прямо: раньше числа были видны по всем хабам сразу и без клика, теперь —
по одному и только кликом по строке. Взамен число получило контекст, которого
у него не было: оно стоит рядом с ценой, объёмом и итогом своего хаба.

### 5.4 Фильтры сторон

Два чекбокса, **«только sell»** и **«только buy»**. Buy-ордер — это заявка, а не покупка:
она может не исполниться и требует времени. Когда газ нужен сегодня, buy-строки — шум,
и их убирает «только sell». Когда важнее цена, а не срок, обратное верно: «только buy»
оставляет одни заявки — газ придёт не сразу и может не прийти вовсе, зато дешевле.

Оба выключены по умолчанию, и это третье осмысленное состояние: показываются все
сценарии. Отсюда чекбоксы, а не радиокнопки — «ни один» пришлось бы рисовать третьей
кнопкой ради того, что и так выражается двумя снятыми галочками.

Вместе они исключают друг друга: в браузере галочки гасят одна другую, а форма,
отправленная без JS с обеими, отвечает ошибкой «Фильтры „только sell“ и „только buy“
исключают друг друга — снимите один». Пустая таблица здесь соврала бы: данные есть,
выдачу схлопнули фильтры.

Точки безубыточности (§5.3) фильтрам не подчиняются: они считаются по ценам sell
и к сторонам выдачи отношения не имеют.

### 5.5 Фильтр «скрыть неликвид»

Чекбокс убирает из таблицы строки с пометкой «сделок по такой цене не было» (§6):
цена стоит вне коридора реальных сделок за неделю, и такой ордер, скорее всего,
не исполнится.

Это **фильтр показа, а не расчёта**. Признак считается по истории сделок, которой
ядро не видит и видеть не должно: `calculator.py` импортирует только stdlib
и `models.py`. Отсюда граница — ядро решает, какие сценарии существуют, интерфейс
решает, какие из них показать. В `CalcInput` поле `hide_illiquid` не попадает.

Что фильтр **не** трогает:

- **Строку без истории.** Нет данных — это «мы не знаем», а не «неликвид».
  Скрыть её значит выдать незнание за факт.
- **Аномальную цену** (отличается от медианы по хабам) и **маленький оборот**.
  Это разные пометки про разное, и склеивать их в одну галочку нельзя.

Приложение ничего не прячет молча. Под таблицей стоит счётчик — «Скрыто строк: N —
по этим ценам за неделю не торговали»; при нуле скрытых он не пишется вовсе.
Сводка в полосе итогов и ширины полосок пересчитываются **по видимым строкам**:
иначе «Лучший вариант» показывал бы строку, которой в таблице нет. Числитель
карточки «Сценариев в расчёте» — количество видимых строк; знаменатель остаётся
числом ячеек сетки цен.

Если фильтр скрыл всё, на экране не «Недостаточно данных», а «Все строки скрыты
фильтром „скрыть неликвид“: по всем ценам за неделю не торговали. Снимите галочку,
чтобы увидеть их». Данные есть — соврать про их отсутствие нельзя.

### 5.6 Фильтр «по одной строке на хаб»

Чекбокс оставляет у каждого хаба одну строку — самую дешёвую из его четырёх
(сырой/сжатый × sell/buy). «Самая дешёвая» — по ISK за полезный юнит, той же
метрике, по которой отсортирована вся таблица: список уже идёт по возрастанию,
поэтому первое вхождение каждого хаба и есть его лучший сценарий.

Тоже **фильтр показа**: `best_per_hub` в `CalcInput` не попадает и читается прямо
в `routes.calculate`. Машинка та же, что у §5.5 — пересчёт сводки по видимым
строкам и счётчик под таблицей: «Показано по одной строке на хаб. Свёрнуто строк:
N — у каждого хаба осталась самая дешёвая». При нуле свёрнутых счётчика нет.

**Порядок с §5.5 зафиксирован: сначала «скрыть неликвид», потом свёртка.** Иначе
хаб мог бы остаться представленным неликвидной строкой, которую вторая галочка
потом уберёт, — и хаб пропал бы целиком, хотя живая альтернатива у него была.
Пропасть из выдачи хаб может только по двум причинам: не задана ставка доставки
или не введено ни одной цены.

Когда появится сортировка кликом по заголовку, она будет применяться **после**
свёртки, а не до: выбор лучшей строки хаба всегда идёт по ISK/юнит независимо
от того, по какой колонке пользователь сортирует таблицу. Иначе при сортировке
по объёму «лучшей» строкой хаба окажется самая объёмная, а не самая выгодная.

### 5.7 Сортировка кликом по заголовку

Заголовки **Хаб, Цена, Купить, м³, Итого и ISK/юнит** сортируют таблицу. Первый
клик — по возрастанию, второй по той же колонке переворачивает порядок; стрелка
у активной колонки показывает текущее направление. Умолчание не меняется:
ISK/юнит по возрастанию — это ответ на главный вопрос приложения, и открываться
страница обязана с ним.

**Сортирует сервер.** Клик кладёт имя колонки и направление в скрытые поля
`sort` и `sort_dir` и дёргает `recalc` — тот же путь, которым ходят все
остальные изменения формы. Сортировка в браузере означала бы второй порядок
правды и разъехалась бы с полосками, которые считаются от размаха. Мусор
в скрытых полях — состояние интерфейса, а не ввод человека: непонятное значение
молча заменяется умолчанием, а не роняет расчёт.

Хаб сортируется в порядке `constants.HUBS`, а не по алфавиту: это привычный
игроку порядок, и он же используется в сетке цен. При равенстве ключей вторым
идёт ISK/юнит по возрастанию — всегда по возрастанию, независимо от выбранного
направления: это не выбор пользователя, а способ не дать одинаковым ключам
плясать между запросами.

**Колонка «#» — место в порядке по ISK/юнит, а не номер строки на экране.**
При сортировке по другой колонке это разные вещи, и полезно из них только
первое: оно говорит, насколько выбранная строка далека от лучшей. По той же
причине подсветка лучшей строки и `Δ` остаются привязаны к лучшему по ISK/юнит,
а не к тому, что оказалось наверху.

Заголовок сортируемой колонки — `<button>` внутри `<th>`, а не обработчик
на самой ячейке: клавиатура и озвучка должны видеть кнопку. На `<th>` стоит
`aria-sort`, и ровно одна колонка в таблице не `none`. Курсор-рука и подсветка
при наведении есть только у сортируемых заголовков — вид элемента не обещает
того, чего он не делает.

Порядок применяется **после** фильтров показа (§5.5, §5.6): лучшую строку хаба
выбирает ISK/юнит независимо от того, по какой колонке смотрит пользователь.

### 5.8 Панель «Разбор строки»

Клик по строке таблицы открывает под ней разбор именно этой строки. Строка
доступна и с клавиатуры: `tabindex="0"` и Enter — кликабельная строка без
клавиатуры для части людей просто не существует.

**Панель рисует сервер, HTMX её подставляет.** Клик шлёт `POST /row-detail`
с той же формой плюс ключ строки; ответ — фрагмент, который ложится в контейнер
под таблицей. Считать те же числа второй раз в браузере нельзя: математика
живёт в ядре, и второй её экземпляр разъедется с первым. Числа в панели —
буквально те же, что в таблице: их собирает тот же `_row_views`.

Ключ строки — `{hub}|{form}|{side}`, тот же, которым свод истории ищет свою
запись. Ключ не нашёлся — пустой ответ и код 200: значит форма изменилась между
кликом и запросом, панель просто не открывается. Ошибку показывать не за что.

Панель показывает три колонки:

1. **Из чего сложился итог** — газ с комиссией, доставка за объём, обеспечение;
   полоска и доли те же, что в колонке таблицы, плюс итог за партию и за юнит.
2. **Рынок хаба** — ваша цена, опора сделок, диапазон за неделю, оборот в сутки
   и за окно, нужное количество, глубина стакана, ставка доставки. Чего мы
   не знаем — сказано словами: глубина при ручном вводе неизвестна, а не ноль;
   истории нет — «мы не знаем», а не «торгов не было»; заимствованный свод
   оборота не показывает вовсе.
3. **Что смущает** — расшифровка значков именно этой строки. Ни один не поднялся —
   так и написано: «Ничего: цена в диапазоне сделок, объём рынок отдаёт, стакана
   хватает». Ниже — точка безубыточности этого хаба, а где её нет, сказано,
   каких цен для неё не хватает.

Панель живёт внутри ответа `/calculate`, поэтому любое изменение параметров
закрывает её само: блок результата приезжает заново и панель в нём пустая.
Внутри неё числа того расчёта, которого уже нет на экране, и оставлять её
открытой значило бы показывать устаревшее рядом со свежим.

**Точка безубыточности показывается только здесь.** Отдельный блок под таблицей
жил до 22.08.2026 и убран по решению пользователя — так и было нарисовано
в макете.

### 5.9 Легенда значков под таблицей

Под таблицей стоит расшифровка трёх значков-пометок — «сделок по такой цене
не было», «аномальная цена», «маленький оборот газа». Блок видно всегда:
раскрывашкой он был до 22.08.2026, но прятать за клик то, ради чего человек
и смотрит в таблицу, незачем.

Кроме легенды в блоке ничего нет. Список сносок, живший там раньше, убран:
после появления панели «Разбор строки» (§5.8) у каждой его строки нашёлся
адресат получше — панель говорит то же самое, но про конкретную строку и её
числами, а не «где-то в таблице». Правило «каждое число на экране объяснено»
при этом осталось в силе, и вот куда что переехало:

| Что объясняла сноска | Где это теперь |
|---|---|
| Пометки строк: неликвид, выброс, объём, глубина стакана | Подсказка на значке, легенда, «Что смущает» в разборе строки |
| Обеспечение внутри «Доставки» | Разбор строки: «Доставка за объём» и «Обеспечение» стоят отдельными строками |
| «По другим хабам» — заимствованный свод | Подпись в ячейке и объяснение в разборе строки |
| Дата, по которую собрана история | Чип «история ДД.ММ.ГГГГ» в шапке |
| Хабы без ставки доставки | Карточка «Сценариев в расчёте»: «без доставки: …» |
| Что сделали фильтры сторон | Сами галочки в панели фильтров; при пустой выдаче — текст пустого состояния |
| Сколько строк скрыли фильтры показа | Счётчики под таблицей (§5.5, §5.6) |

## 6. Предупреждения

Показываются как пометка на строке таблицы и расшифровкой под ней.

| Условие | Текст |
|---------|-------|
| Глубины стакана не хватает на нужный объём (только для цен из базы) | «В стакане только N юнитов из M» |
| Цена отличается от медианы по остальным хабам больше чем в 3 раза | «Цена сильно выбивается — проверьте» |
| Цена вне диапазона реальных сделок за неделю (`ESI.md` §5.5) | «Неликвидная цена: сделок по ней не было» |
| Нужный объём больше недельного оборота | «За неделю в регионе продано N юнитов — столько не набрать» |
| Нужный объём больше среднесуточного оборота | «В сутки торгуют N юнитов — набирать придётся несколько дней» |
| Вся книга хаба выброшена как неликвид (`ESI.md` §5.4) | «Ликвидных ордеров нет» |
| По хабу нет свежего среза | «Данных нет по хабам: …» |
| Ставка доставки не задана | «Не задана доставка» |

Никаких молчаливых нулей и подстановок по умолчанию. Если данных нет — так и написать.

Место, где предупреждение показывается, с 22.08.2026 одно и то же для всех:
пометка-значок на строке с подсказкой, расшифровка значка в легенде под таблицей
и полный текст в разборе строки (§5.9). Общего списка сносок под таблицей больше
нет — он говорил про таблицу целиком, а вопрос у человека всегда про строку.

## 7. Сохранение настроек

Сохраняются:

- ставки доставки по всем пяти хабам,
- газ и нужное количество юнитов,
- тип структуры, уровень GDE, брокерский процент,
- процент обеспечения,
- состояние чекбоксов,
- выбранный порядок таблицы (§5.7),
- тема оформления.

**Не сохраняются** цены — они устаревают за минуты, и подставить вчерашнюю цену
вместо свежей в калькуляторе денег хуже, чем не подставить ничего.

Место хранения зависит от того, вошёл пользователь или нет:

| | Аноним | Вошедший |
|---|---|---|
| Где лежит | `localStorage`, ключ `gascalc.settings` | база, таблицы `user_settings` и `user_freight_rate` |
| Когда пишется | при изменении любого поля формы | при изменении любого поля, `POST /settings/save` |
| Когда читается | при загрузке страницы, до первого рендера | на сервере, при сборке страницы |
| Что переживает | этот браузер | смену браузера и машины |

Анонимные настройки восстанавливаются до первого рендера, чтобы форма не мигала.

### 7.1 Тема оформления

Тема — не поле формы: её ставит кнопка в шапке, а не расчёт. Хранится она тем
не менее вместе с остальными настройками, и правило то же: **у вошедшего
побеждает аккаунт.** Настройка, которая не переезжает между машинами, — это
ровно то, что здесь чинится; у анонима всё остаётся как было, в `localStorage`.

Тема применяется до первой отрисовки. У вошедшего сервер знает её на момент
рендера и ставит `data-theme` прямо в `<html>`; скрипт в `<head>` перебивать
её не имеет права и читает `localStorage` только тогда, когда атрибута нет.
Перепутанный порядок здесь даёт мигание светлым на тёмной странице — ровно то,
ради чего скрипт в `<head>` и появился. Без атрибута страница тёмная: умолчание
задано в `:root`, а не в разметке, поэтому до выполнения скрипта она не «никакая».

Кнопка темы шлёт на `/settings/save` запрос из одного поля `theme`. Обычный
`save` затирает незаполненные поля — так работает и сброс настроек пустой
формой, — поэтому такой запрос обрабатывается отдельным путём и, кроме темы,
ничего не касается. Значение проверяется по белому списку `{dark, light}`:
приходит оно из браузера, а оттуда может прийти что угодно. Мусор, оказавшийся
в базе, читается как «не выбирал» — остаётся тёмная.

Системная тема (`prefers-color-scheme`) не учитывается: умолчание тёмное,
и это сознательно. Открывать страницу по системной настройке у тех, кто ещё
ничего не выбирал, — отдельное решение, оно меняет вид приложения при первом
заходе.
У вошедшего значения уже приехали с сервера в самом HTML, и `localStorage`
не читается вовсе — иначе настройки из чужого браузера перебивали бы свои.

Кнопка «Сбросить настройки» рядом с блоком параметров чистит оба хранилища:
у вошедшего мало очистить браузер — при следующей загрузке настройки приехали бы
обратно с сервера.

## 8. Аккаунт и вход через EVE SSO

**Вход нужен ровно для одного: хранить настройки на сервере, а не в браузере.**
Ничего другого аккаунт не даёт и давать не должен.

### Что доступно анониму

Всё. Выбор газа, сетка цен, расчёт, точки безубыточности, предупреждения,
сохранение настроек в браузере. Анонимный режим — основной, а не урезанный:
если вход не настроен на сервере или CCP лежит, приложение продолжает считать,
и ссылки на вход просто нет.

Единственное, чего у анонима нет, — настройки не переезжают в другой браузер.

### Что видит вошедший

- портрет и имя персонажа и кнопку «Выйти» в шапке;
- свои настройки на любой машине, где он вошёл;
- при первом входе — предложение забрать настройки, накопленные в этом браузере
  анонимно. Отказ ничего не портит: в браузере они остаются.

### 8.1 Портрет персонажа

Картинка берётся с `https://images.evetech.net/characters/{id}/portrait?size=64` —
публичный сервис CCP, авторизации не требует. Приложение за ней **не ходит**
и её не кэширует: в HTML уходит адрес, а картинку тянет браузер пользователя.

На 20.08.2026 это **единственный внешний адрес на странице** — не потому, что
внешние запрещены (`CLAUDE.md`, «Внешние запросы»), а потому, что остальное
дешевле и надёжнее раздать со своего хоста. Как он устроен:

- **один запрос на загрузку страницы и только у вошедшего.** Дальше картинку
  держит кэш браузера: портрет персонажа не меняется годами;
- **буква в кружке остаётся и никуда не девается.** Она лежит под портретом:
  видна, пока картинка грузится, и остаётся, если картинка не пришла. Битая
  картинка убирается с экрана — значка обрыва на месте аватара не бывает;
- **есть выключатель.** `CHARACTER_PORTRAITS = False` возвращает букву и убирает
  внешний адрес со страницы. Нужен тому, кто разворачивает приложение в закрытом
  контуре или просто не хочет отдавать этот запрос наружу;
- **`referrerpolicy="no-referrer"`**: серверу CCP незачем знать, с какой страницы
  пришёл запрос за картинкой.

Цена названа прямо: браузер вошедшего пользователя обращается к серверу CCP,
и CCP видит этот запрос. У анонима портрета нет — ему нечего показывать.

### Чего приложение не знает о персонаже

Запрашивается **пустой список scope**: ни кошелька, ни навыков, ни ассетов, ни
корпорации. Из токена берутся только `character_id` и имя — этого хватает, чтобы
понять, чьи настройки грузить. Refresh-токен не сохраняется: приватных данных мы
не читаем, а любой сохранённый секрет — это то, что можно потерять.

### Правила безопасности

- токен принимается только с проверенной подписью (JWKS CCP), верным `issuer`,
  `audience` и непросроченным сроком. Токен без проверки подписи не принимается
  никогда — иначе кто угодно называется кем угодно;
- `state` проверяется и одноразовый, живёт в подписанной сессии, а не в базе;
- кука сессии в профиле prod — `Secure`, `HttpOnly`, `SameSite=Lax`;
- `SSO_REDIRECT_URI` обязан посимвольно совпадать с колбэком, зарегистрированным
  у CCP.

## 10. Оформление

Интерфейс называется **GasLens Terminal**. Макет получен от пользователя 19.08.2026
и лежит в каталоге `EveGAS_calc дизайн/` — он справочный, в раздачу не входит и
зависимостью приложения не является. Макет — источник вёрстки, палитры и типографики.
Он **не** источник чисел и не источник кода: данные в нём выдуманные, формулы упрощены,
логика написана на React. Математика остаётся в `app/core/calculator.py`, значения —
в `docs/DOMAIN.md`.

Прежняя редакция этого раздела требовала обратного — «системный шрифт, никаких иконок,
шрифтов, анимаций и тем, один `style.css` на 100–150 строк». Она действовала, пока
расчёт не был готов, и с версии 0.3.0 отменена целиком.

### 10.1 Что осталось запрещено

Оформление стало плотнее, но ограничения проекта не сдвинулись:

- никакого CSS-фреймворка, npm, сборщиков и препроцессоров: один `app/static/style.css`,
  написанный руками;
- внешние адреса на странице — по списку, а не по запрету (`CLAUDE.md`, раздел
  «Внешние запросы»). Полный список на 20.08.2026 — **один**: портрет вошедшего
  персонажа с `images.evetech.net` (§8.1). Всё остальное раздаётся со своего
  хоста, и по умолчанию новое тоже раздаётся со своего: шрифт, положенный файлом,
  это одна раздача вместо запроса к CDN на каждую загрузку страницы у каждого
  пользователя. Внешний адрес добавляется, когда он того стоит, — но осознанно
  и в этот список;
- ни один внешний адрес не имеет права сломать страницу. Не загрузившийся шрифт
  оставляет запасное семейство, не пришедшая картинка — букву в кружке. Дыры,
  значка обрыва и бесконечного ожидания на экране быть не должно;
- никаких иконочных шрифтов и SVG-библиотек. Значки при этом ровно те, что
  нарисованы в макете, и рисуются они его же разметкой: SVG в шаблоне, линии
  через `currentColor`, десяток строк на значок. Запрещена зависимость, а не
  картинка. Подменять рисунок макета символом (`⊘`, `!`, `↓`) нельзя: в рамке
  18 px символ читается значком только в мыслях того, кто его поставил,
  а три пометки подряд перестают различаться;
- анимации — только служебные (наведение, смена темы, раскрытие блока сносок).
  Декоративного движения на экране нет.

### 10.2 Главное правило раздела

**Ни одно число, ни одна пометка и ни одно состояние не должны пропасть с экрана.**
Макет нарисован в одном состоянии: вошедший пользователь, данные есть, ошибок нет.
Всё остальное — аноним, флеш-сообщения, «Расчёт не выполнен», «Недостаточно данных»,
заметки сетки цен, сноски, точки безубыточности — дорисовывается в стиле макета.
Отсутствие элемента в макете не является разрешением его убрать.

Контракт формы при этом не меняется: имена полей `{hub}_rate`, `{hub}_{suffix}`,
`{hub}_{suffix}_auto`, `{hub}_{suffix}_depth` остаются как есть — на них держатся
`_parse_form`, `_build_grid` и `settings.js`.

### 10.3 Токены и темы

Цвета задаются CSS-переменными на корневом элементе и берутся из макета один в один,
а не подбираются на глаз:

| Группа | Переменные |
|--------|------------|
| Фон и панели | `--bg`, `--panel`, `--panel2`, `--input` |
| Линии | `--line`, `--lineSoft` |
| Текст | `--fg`, `--fg2`, `--fg3` |
| Сырой газ | `--rawFg`, `--rawBg`, `--rawLine` |
| Сжатый газ | `--compFg`, `--compBg`, `--compLine` |
| Сторона сделки | `--sellFg`, `--sellBg`, `--buyFg`, `--buyLine` |
| Акценты | `--gold`, `--cyan`, `--green`, `--amber`, `--red` |
| Строки таблицы | `--bestBg`, `--rowAlt`, `--hover` |

Два набора значений: `[data-theme="dark"]` и `[data-theme="light"]`. **Тёмная тема —
по умолчанию.** Выбор хранится в `localStorage` и применяется до первой отрисовки,
иначе страница мигает светлым. Переключатель — в шапке.

Инлайновых стилей в шаблонах не остаётся: всё, что в макете написано в `style="…"`,
переезжает в классы. Единственное исключение — значения, зависящие от данных
(ширина полоски, цвет по порогу). Такие значения считает сервер и передаёт
в шаблон отдельным полем; арифметики в шаблоне быть не должно.

### 10.4 Шрифты

`Inter` для текста и `JetBrains Mono` для чисел — оба лежат в `app/static/fonts/`
файлами `woff2` и раздаются со своего хоста через `@font-face` с `font-display: swap`.
Лицензия обоих — SIL OFL, вложение в репозиторий разрешено. Запасные семейства
обязательны: `system-ui, sans-serif` и `ui-monospace, monospace` — если шрифт
не загрузился, страница остаётся читаемой.

Файлов восемь, а не двадцать: шрифты вариативные, и один файл на подмножество
символов обслуживает все начертания. Поэтому `font-weight` в `@font-face` задан
диапазоном, а не числом на каждый вес. `unicode-range` режет загрузку
по алфавитам — на русской странице браузер берёт четыре файла из восьми.

**Кириллица обязательна у текстового шрифта.** Интерфейс русский: подписи полей,
заголовки колонок и сноски — всё это кириллица, и если её нет в семействе,
браузер молча подставляет системный шрифт, а оформление применяется к меньшей
части экрана. Так было в 0.3.0 с `Archivo` из макета, у которого кириллического
подмножества нет вовсе; 20.08.2026 он заменён на `Inter`. Подробности и причина,
по которой отвергнут смешанный стек из двух семейств, — в `app/static/fonts/README.md`.

Отсюда правило на будущее: **шрифт из макета проверяется на кириллицу до того,
как попадёт в `style.css`.** Замер простой — ширина русской строки в этом шрифте
и в заведомо несуществующем: совпала, значит шрифт не применяется.

Google Fonts из макета в приложение не переносится: `<link>` на сторонний хост
означает запрос к нему на каждую загрузку страницы у каждого пользователя,
а не загрузившийся шрифт — прыгающую вёрстку. Файлом это одна раздача (§10.1).

Числа набираются моноширинным шрифтом с `font-variant-numeric: tabular-nums` —
колонки цен должны выравниваться по разрядам.

### 10.5 Каркас страницы


Схема из §2 описывает состав экрана, а не его расположение: с версии 0.3.0 параметры
и сетка цен стоят в левой колонке, результат — в правой.

- шапка: имя продукта, текущий газ и его объёмы, чипы состояния данных
  (состояние Tranquility, возраст цен и дата истории, номер версии), растяжка,
  переключатели, блок аккаунта. При нехватке места второстепенные чипы переносятся
  или прячутся, но имя продукта, текущий газ и блок аккаунта видны всегда;
  номер версии берётся из `app/version.py` — единственного места, где он записан,
  и стоит среди чипов состояния, потому что отвечает на тот же вопрос: чем
  и по каким данным считали;
- панель фильтров липнет под шапкой (`top: 48px`);
- таблица результата прокручивается горизонтально внутри своего контейнера
  (`min-width: 1060px`, `overflow-x: auto`); страница целиком горизонтально не едет;
- ниже ~1000 px колонки складываются в одну: параметры и сетка цен над результатом.

**Полоса итогов идёт над колонками, во всю ширину.** Считается она в `/calculate`,
который отвечает фрагментом для `#results` в правой колонке, поэтому полоса приезжает
тем же ответом через `hx-swap-oob="true"`. Второго запроса ради четырёх карточек нет.

### 10.6 Пересчёт

Автоматический при изменении любого поля, как и раньше. Кнопка «Посчитать» в макете
не нарисована, но в приложении остаётся: это страховка на случай, когда автопересчёт
не сработал. Рисуется она неброско и на своём месте — под параметрами.

### 10.7 Элементы, к которым ещё нет функционала

Из макета они не убираются — решение пользователя от 19.08.2026. Но и врать они
не должны: кнопка, которая молча ничего не делает, хуже отсутствующей. Такой элемент
рисуется **неактивным**: атрибут `disabled` (или `aria-disabled` там, где `disabled`
неприменим), приглушённый цвет и подсказка `title="функционал ещё не сделан"`.

В этом списке остался один элемент: переключатель RU / EN.

Из списка вышли 20.08.2026: спарклайн «7 дней» (§5.2), чип состояния сервера
(`ESI.md` §8), портрет персонажа (§8.1), все четыре фильтра панели —
«только buy» (§5.4), «скрыть неликвид» (§5.5) и «по одной строке на хаб» (§5.6), —
сортировка кликом по заголовку (§5.7), панель «Разбор строки» (§5.8) и тема
оформления в настройках аккаунта (§7). Полный список с решениями по ходу —
в `docs/ROADMAP.md`, раздел «Элементы макета, к которым ещё нет функционала».

Заголовки таблицы, по которым сортировки нет, рисуются обычным текстом — без
стрелок и без курсора-руки. Вид элемента не обещает того, чего он не делает.
С 20.08.2026 таких заголовков восемь из четырнадцати, остальные шесть сортируют
(§5.7).
