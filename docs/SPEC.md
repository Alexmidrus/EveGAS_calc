# SPEC.md — функциональные требования

Формулы и константы — в `docs/DOMAIN.md`. Здесь только «что видит и делает пользователь».

---

## 1. Сценарий использования

Промышленник в EVE Online собирается закупить партию газа для реакций. Газ торгуется в
двух формах — сырой (объёмный, годен для производства сразу) и сжатый (в 10 раз компактнее,
но перед использованием теряет 5–20% при разжатии). Дешевле возить сжатый, но купить
придётся больше. Цены и глубина стакана в пяти хабах разные, стоимость доставки из каждого
хаба тоже разная.

Пользователь открывает страницу, выбирает газ, вводит параметры, видит **одну таблицу**
и понимает, куда лететь сегодня. Всё.

---

## 2. Одна страница, три блока

```
┌─────────────────────────────────────────┐
│  Блок 1. Параметры расчёта              │
├─────────────────────────────────────────┤
│  Блок 2. Сетка цен 5×4                  │
├─────────────────────────────────────────┤
│  Блок 3. Результат: сводка + таблица    │
└─────────────────────────────────────────┘
```

Пересчёт — по кнопке «Посчитать» либо автоматически при изменении любого поля (через HTMX,
с debounce). Начни с кнопки, автопересчёт добавь на этапе полировки.

---

## 3. Блок 1 — параметры

| Поле | Тип | По умолчанию | Валидация |
|------|-----|--------------|-----------|
| Газ | select, все типы из `data/gases.json`, сгруппированы по семействам | Fullerite-C320 | обязательно |
| Нужно юнитов сырого | int | 10000 | > 0 |
| Тип структуры | select: Upwell / Athanor / Tatara | Athanor | — |
| Навык Gas Decompression Efficiency | select 0..5 | 5 | 0..5 |
| Брокерская комиссия, % | float | 1.5 | 0..5 |
| Обеспечение, % от стоимости газа | float | 0.5 | 0..100 |

Рядом с полем структуры и навыка — **живой вывод итоговой эффективности**: «Разжатие: 89%».
Пользователь должен видеть, что он настроил, не открывая справочник.

Под селектом газа — объёмы выбранного типа: «5 м³ сырой / 0.5 м³ сжатый».

---

## 4. Блок 2 — сетка цен

Таблица 5 строк × 5 колонок. Строки — хабы в порядке из `DOMAIN.md`.

| Хаб | Доставка, ISK/м³ | Сырой sell | Сырой buy | Сжатый sell | Сжатый buy |
|-----|------------------|------------|-----------|-------------|------------|
| Jita | [input] | [input] | [input] | [input] | [input] |
| Amarr | [input] | [input] | [input] | [input] | [input] |
| ... | | | | | |

**Все ячейки заполняются вручную.** Это основной режим ввода. Ставка доставки своя
у каждого хаба — это отдельная колонка, не общее поле.

Поведение при незаполненных ячейках:

- Пустая цена → соответствующий сценарий **не попадает** в результирующую таблицу. Не ноль, не ошибка — просто отсутствует.
- Пустая ставка доставки → все четыре сценария этого хаба выпадают, строка помечается как «не задана доставка».
- Заполнена хотя бы одна ячейка → расчёт возможен.

Над сеткой — кнопка **«Подтянуть цены из ESI»**. Заполняет все 20 ценовых ячеек
автоматически (см. `docs/ESI.md`). Ставки доставки не трогает — их ESI не знает.
Подтянутые значения визуально отличаются от введённых вручную (например, приглушённый цвет),
и пользователь может перебить любую из них.

Ручной ввод — мастер. ESI — черновик.

## 5. Блок 3 — результат

### 5.1 Сводка

Три числа крупно:

- **Лучший вариант** — ISK за полезный юнит + подпись «Amarr, сжатый, buy».
- **Разница с худшим** — сколько ISK экономит лучший вариант на всей партии.
- **Потери при разжатии** — сколько юнитов сгорит и сколько это процентов. Показывать только если в выдаче есть сжатые сценарии.

### 5.2 Основная таблица

Колонки:

| Колонка | Содержимое |
|---------|------------|
| Хаб | название |
| Что берём | «сжатый · buy» и т.п. |
| Цена | цена за юнит, как введена |
| Купить | сколько юнитов покупаем (для сжатого — с запасом на потери) |
| Объём | м³ груза |
| Доставка | ISK: объём × ставка плюс надбавка за обеспечение |
| Итого | ISK |
| ISK/юнит | **главная колонка**, по ней сортировка по возрастанию |
| Δ | отставание от лучшего варианта в процентах, у первой строки прочерк |

Первая строка выделена. Строки с предупреждениями помечены.

### 5.3 Точки безубыточности

Под таблицей — по строке на каждый хаб, где заполнены обе цены sell:

> Jita: сжатый выгоднее сырого, пока стоит дешевле **4 645 ISK**

Считается по формуле из `DOMAIN.md`. Если одна из цен не введена — строка не показывается.

### 5.4 Фильтр

Чекбокс **«только sell»**. Buy-ордер — это заявка, а не покупка: она может не исполниться
и требует времени. Когда газ нужен сегодня, половина строк — шум. По умолчанию выключен,
показываются все сценарии.

## 6. Предупреждения

Показываются как пометка на строке таблицы и расшифровкой под ней.

| Условие | Текст |
|---------|-------|
| Глубины стакана не хватает на нужный объём (только при данных из ESI) | «В стакане только N юнитов из M» |
| Цена отличается от медианы по остальным хабам больше чем в 3 раза | «Цена сильно выбивается — проверьте» |
| ESI не ответил по этому хабу | «Данные не получены» |
| Ставка доставки не задана | «Не задана доставка» |

Никаких молчаливых нулей и подстановок по умолчанию. Если данных нет — так и написать.

## 7. Сохранение настроек

`localStorage`, ключ `gascalc.settings`. Сохраняются:

- ставки доставки по всем пяти хабам,
- тип структуры, уровень GDE, брокерский процент,
- процент обеспечения,
- состояние чекбоксов.

**Не сохраняются** цены — они устаревают за минуты.

Восстановление — при загрузке страницы, до первого рендера, чтобы не мигало.
Кнопка «Сбросить настройки» рядом с блоком параметров.

## 8. Эндпоинты

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/` | страница с формой |
| POST | `/calculate` | принимает форму, возвращает HTML-фрагмент блока 3 (HTMX) |
| POST | `/fetch-prices` | подтягивает цены из ESI, возвращает HTML-фрагмент сетки цен |
| GET | `/api/gases` | JSON-справочник газов, для клиентского JS |

`/calculate` и `/fetch-prices` возвращают фрагменты, а не полные страницы — это HTMX.

## 9. Оформление

На текущем этапе — **минимальное**. Системный шрифт, таблица с рамками, две-три подсветки
(лучший вариант, предупреждение), никакого CSS-фреймворка, никаких иконок, шрифтов с CDN,
анимаций и тем. Один файл `static/style.css` на 100–150 строк.

Дизайн делаем отдельной задачей после того, как расчёт работает и покрыт тестами.
Не тратить на него время сейчас.
