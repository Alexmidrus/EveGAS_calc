какие решения приняты по ходу.

# Версия 0.1.0 — этапы 5–10

Версии 0.0.x были stateless: ни базы, ни аккаунтов, ни фоновых задач. Версия 0.1.0
осознанно снимает эти ограничения. Решение согласовано с пользователем 17.08.2026,
жёсткие ограничения в `CLAUDE.md` обновлены тем же решением.

**Что меняется по сути.** Раньше нагрузка на ESI была пропорциональна числу
пользователей: каждый жал «Подтянуть цены» и тратил 10 запросов. При 100–200
пользователях это верный путь к бану. Теперь ESI опрашивает один сборщик по
расписанию, а пользователи читают из базы и на ESI не влияют вообще.

**Принятые решения по развилкам:**

- **Планировщик — системный cron.** Сбор запускается командой `python -m app.jobs.collect`,
  расписание задаёт cron на Linux или Планировщик задач на Windows. Ноль новых
  зависимостей, нет дублирования при нескольких воркерах waitress, падения и логи
  видны отдельно от веб-процесса.
- **Слой БД — SQLAlchemy + Alembic.** Один код на SQLite, MySQL/MariaDB и Postgres.
  Ручной SQL под три диалекта в приложении, которое считает деньги, — источник
  расхождений, которые не видно глазом.
- **Бюджет зависимостей растёт с 4 до 9**: добавляются `SQLAlchemy`, `alembic`,
  `psycopg[binary]`, `PyMySQL`, `PyJWT[crypto]`. Больше пятой зависимости на 0.1.0
  не добавлять без отдельного согласования.

**Правило версионирования.** Номер версии поднимается только при появлении нового
функционала. Исправления, рефакторинг, документация и правки уже реализованной
механики версию не двигают. Поэтому вся работа по этапам 5–9 идёт под номером
`0.0.1`, а `0.1.0` ставится один раз — на этапе 10, когда весь функционал версии
готов и проверен.

**Посылки, на которых построен план:**

- Анонимный вход остаётся. SSO нужен только для хранения настроек на сервере;
  без логина приложение работает как в 0.0.x, настройки — в `localStorage`.
- Ручной ввод цен остаётся. Убирается только кнопка «Подтянуть цены из ESI».
- В базе лежит не готовая цена, а **очищенная лестница стакана**. VWAP зависит от
  нужного пользователю `N`, заранее его не знаешь. Храня лестницу, считаем VWAP
  на запрос уже протестированными функциями `orderbook.py` — математика не трогается.

Этапы 8 и 9 зависят только от базы и между собой не связаны: их можно поменять
местами. Порядок ниже ставит сборщик раньше SSO, потому что сборщик меняет то,
как цены попадают на экран, а SSO — надстройка сбоку.

## Этап 5. Два профиля запуска: dev и prod

Ничего не работает иначе, но всё дальнейшее опирается на профиль: адрес базы,
секреты, поведение планировщика.

- [x] `app/config.py` — загрузка профиля по переменной окружения `APP_ENV` (`dev` | `prod`), по умолчанию `dev`
- [x] Профиль `dev`: SQLite-файл, `DEBUG=True`, подробные страницы ошибок, сбор цен не требуется
- [x] Профиль `prod`: внешняя СУБД, `DEBUG=False`, секреты **только** из переменных окружения
- [x] Секреты в переменных окружения: `SECRET_KEY`, `DATABASE_URL`, `ESI_CLIENT_ID`, `ESI_CLIENT_SECRET`
- [x] Валидация конфига при старте: `prod` без `SECRET_KEY` или `DATABASE_URL` падает сразу с понятным текстом, а не на первом запросе пользователя
- [x] Запрет на `DEBUG=True` в профиле `prod` — проверкой в коде, а не комментарием
- [x] `config.example.py` переписать под два профиля; сохранить `ESI_USER_AGENT` и `ESI_COMPATIBILITY_DATE`
- [x] `tests/test_config.py`: `create_app()` поднимается в обоих профилях; `prod` без секретов падает; `prod` с `DEBUG=True` падает
- [x] README: раздел «Профили запуска», таблица переменных окружения

Проверка: `APP_ENV=dev python run.py` поднимается как раньше; `APP_ENV=prod python run.py`
без переменных окружения падает с внятным сообщением, а не стектрейсом на первом запросе.

Решения, принятые по ходу этапа:

- **Три слоя вместо одного файла.** Было: `config.py` целиком заменяет настройки,
  а при его отсутствии читается `config.example.py`. Стало: умолчания профиля
  в `app/config.py` → `config.py` → переменные окружения. Умолчания переехали
  в код, `config.example.py` стал шаблоном и перестал быть источником истины —
  иначе два места с одними и теми же числами неизбежно разъезжаются.
- **Профиль задаётся только через `APP_ENV`.** `config.py` его переопределить
  не может: иначе прод-запуск мог бы молча оказаться dev-запуском. На это есть тест.
- **`build_config(environ, base_dir)` вместо чтения `os.environ` напрямую.**
  Оба аргумента нужны тестам: иначе результат зависит от переменных окружения
  машины и от того, лежит ли рядом чей-то `config.py`. `create_app(config=...)`
  по той же причине принимает готовую конфигурацию.
- **Валидация дала два запрета сверх задания.** SQLite в `DATABASE_URL` на проде
  отвергается: сборщик цен будет писать из отдельного процесса одновременно
  с веб-приложением, а SQLite такую запись не выдерживает. Шаблонный
  `ESI_USER_AGENT` на проде тоже отвергается — это прямой путь под рейт-лимит.
  В `dev` оба случая проходят, второй с предупреждением.
- **`ESI_CACHE_TTL` меньше 300 секунд запрещён в обоих профилях.** Правило
  «не кэшировать агрессивнее ESI» из `CLAUDE.md` стало проверкой в коде.
- **Проверка сработала на живом примере.** Первый же запуск `APP_ENV=prod`
  упал на `DEBUG=True` из локального `config.py` — ровно тот случай, ради
  которого проверка и делалась: dev-конфиг уехал на прод как есть.

Проверка: `alembic upgrade head` отрабатывает на SQLite, MariaDB, MySQL и Postgres;
тесты на SQLite зелёные.

Решения, принятые по ходу этапа:

- **Внешние ключи в SQLite включены принудительно.** SQLite по умолчанию их не
  проверяет, а MariaDB, MySQL и Postgres проверяют. Без `PRAGMA foreign_keys=ON`
  ограничения молча не работали бы в разработке и внезапно заработали на проде —
  ровно то расхождение диалектов, ради устранения которого брали SQLAlchemy.
  PRAGMA ставится на каждое соединение событием движка.
- **`naming_convention` у метаданных.** Иначе SQLite создаёт безымянные ограничения,
  и Alembic потом не может их изменить.
- **`render_as_batch=True` в Alembic.** SQLite не умеет `ALTER TABLE` как остальные:
  batch-режим пересоздаёт таблицу целиком. Без него любая будущая правка колонки
  на SQLite упадёт.
- **Адрес базы Alembic берёт из `app.config`, а не из `alembic.ini`.** Строка
  `sqlalchemy.url` там оставлена пустой: два места с одним адресом разъезжаются.
- **Автокоммита на выходе из запроса нет.** Сессия закрывается, коммит — забота
  того кода, который менял данные. Автоматический коммит прячет ошибки и
  записывает половину незавершённой операции.
- **Деньги в базе `Numeric`, в лестнице — строками.** Расчёт остаётся во `float`
  по правилу проекта, преобразование на границе. Смысл в том, чтобы база
  возвращала ровно то, что в неё положили, и не накапливала дрейф.
- **Время в базе — наивный UTC.** MySQL и SQLite не хранят зону, поэтому
  единственный переносимый вариант — договорённость плюс хелпер `utcnow()`.
- **Появился `tests/test_db_dialects.py`.** Живых серверов нет, но DDL под каждый
  диалект рендерится без подключения. Это ловит типовые расхождения: `VARCHAR`
  без длины, имя длиннее 64 символов, `Float` в денежной колонке. Ручной прогон
  на настоящих СУБД он не заменяет, но и не даёт уехать вслепую.

# Версия 0.2.0 — этап 11

Первый этап после 0.1.0. Решение согласовано с пользователем 19.08.2026.

**Зачем.** Приложение отвечает на один вопрос: какой газ и где сегодня выгоднее купить,
сжатый или сырой, с учётом цены и доставки. История сделок нужна ровно для одного —
**чтобы в этот ответ не попадали цены, по которым газ на самом деле не торгуется.**
Повод конкретный: buy-ордер в Rens на 1 ISK при реальной цене газа 6000 и выше.

Сегодняшняя защита — правило «×100 от медианы книги» (ESI §4) — берёт опору из той же
книги, которая и врёт. Пока мусор в меньшинстве, это работает. Проверено на живом
`orderbook.py` 19.08.2026:

| Книга buy-ордеров | Что оставляет фильтр |
|---|---|
| один ордер по 1 ISK, три по 6000 | `6000, 6000, 5900` — верно |
| три ордера по 1 ISK, один по 6000 | `1, 1, 1` — **выброшен настоящий ордер** |

Вторая строка — это и есть Rens. Коэффициентом это не лечится: опору надо брать снаружи.
ESI отдаёт по каждому типу и региону дневные итоги реальных сделок, и цена, по которой
газ действительно торговали, как раз такой опорой и работает.

**Что уже выяснено и записано в `docs/ESI.md` §5** (проверено живыми запросами 18.08.2026):

- эндпоинт `GET /markets/{region_id}/history/?type_id=`, публичный, без авторизации;
- отдаёт сразу около 412 дней — накапливать историю самим не нужно;
- **в группы рейт-лимита не входит вообще**: ни одного заголовка `X-Ratelimit-*`
  в ответе, в отличие от `/orders/`;
- обновляется раз в сутки, `Expires` на 11:05 UTC следующего дня — отсюда один заход
  в сутки и 270 запросов в день;
- данные **региональные**: разбивки по станциям нет, разделения buy и sell нет,
  внутридневных значений нет.

**Границы этапа.** История — фильтр и проверка, но не цена. Итоговую цену по-прежнему
даёт VWAP по стакану под фактический объём пользователя; подставлять в расчёт дневную
среднюю нельзя (`ESI.md` §5.6).

Работает это на двух уровнях, и путать их не надо:

- **жёстко и молча** — мусорные ордера выбрасываются из книги ещё у сборщика (§5.4).
  Действует только на цены из базы;
- **мягко и на виду** — в таблице результата появляются колонки «Сделки» и «Продано»,
  а строка с ценой вне диапазона реальных сделок помечается как неликвидная (§5.5).
  Действует на любую цену, включая введённую руками, и ничего не пересчитывает.

Графиков, истории по дням и «динамики рынка» по-прежнему нет — это другое приложение.

## Этап 11. История сделок как внешняя опора цены

Этап меняет числа, за которыми человек пришёл. Порядок работ поэтому обратный
привычному: сначала собрать данные, потом **измерить** на них будущий фильтр,
и только потом включать его в расчёт.

Одно исключение из этого порядка: перенос очистки книги из сборщика в чтение (11.4)
имеет смысл сделать раньше измерения. Пока он не сделан, в базе лежат лестницы, уже
испорченные старым правилом, и мерить на них подбор коэффициентов бессмысленно.

### 11.3 Измерение — до включения фильтра

Отдельный подэтап намеренно. Коридор теперь умеет оставить хаб вовсе без цены, если

ошибка при неверном коэффициенте. Число `4.0` из `ESI.md` §5.4 взято умозрительно,
и включать по нему фильтр, не посмотрев на данные, нельзя.

- [x] Разовый скрипт в `tools/`: прогнать коридор по собранной истории и сохранённым
      срезам стакана, посчитать, сколько ордеров он отбрасывает
- [x] Глазами посмотреть выборку отброшенного: там должны быть скам и мусор, а не

- [x] Отдельно пересчитать, сколько хабов коридор оставляет без цены целиком, и по
      каждому такому случаю убедиться руками, что книга там действительно мусорная
- [x] Отдельно подобрать мягкий `HISTORY_WARN_FACTOR`: он не режет, но помечает строку,
      и слишком тесный порог превратит пометку в шум, на который перестанут смотреть.

- [x] Итоговые числа и выбранные пороги записать в отчёт этапа и в `ESI.md` §5.4

      по объёму. Чистый модуль, 23 теста на фикстурах

**Результат замера.** Коридор отбросил 222 уровня из 3917 (5.7%) и обнулил 6 книг.
Все шесть состояли ровно из одного ордера — 1 ISK или 0.01 ISK при опорных ценах
от 3389 до 155 000. Среди них тот самый `rens buy Fullerite-C84` по 1.00 при опорной
цене 8700, с которого всё началось.

**Пороги пришлось развести.** Симметричный коридор ×4 резал сверху честные ордера:
на тонких газах sell в 4–8 опорных цен — обычное дело, а ближайший к порогу отброшенный
был ×4.05. Снизу картина другая: настоящие buy жались к опоре, весь мусор лежал ниже
×0.12, между ними пустота. Отсюда асимметрия ÷4 и ×10 — и обоснование не в красоте,
а в цене ошибки: мусор снизу даёт неправильный совет, завышенный sell просто проигрывает
сравнение.

**Вторая находка.** 92 книги из 427 состоят из единственного уровня. Правило «×100
от медианы книги» на них не работает вообще: медиане не с чем сравниваться, и любой
ордер проходит в расчёт как есть. Это ровно те книги, где мусор и живёт.

**Третья находка, не про фильтр.** Лестницы, пришедшие с ответом `304`, остаются
в базе в старом виде до первого же изменения стакана. Для замера пришлось разово
сбросить `etag`; в бою это не проблема — на живом рынке ETag меняется за минуты.

### 11.5 Интерфейс

Пользователь должен видеть не «историю», а ответ на два вопроса: правда ли по этой
цене торгуют и получится ли по ней набрать нужный объём.

- [x] Колонка **«Сделки»** в таблице результата: опорная цена за неделю, под ней мелким —
      диапазон `min … max` реальных сделок. Нет истории — прочерк, а не ноль
- [x] Колонка **«Продано»**: среднесуточный оборот этого типа в регионе хаба
- [x] Пометка строки **«неликвидная цена: сделок по ней не было»** — цена вне диапазона
      шире, чем на `HISTORY_WARN_FACTOR` (`ESI.md` §5.5). Работает и для введённых
      руками цен: там жёсткого фильтра нет вообще, и это единственная защита
- [x] Пометка строки по объёму: потребность больше недельного оборота — «столько
      не набрать»; больше среднесуточного — «набирать придётся несколько дней».
      Сравнивать потребность в сжатом с оборотом сжатого, а не сырого
- [x] Пометки не удаляют строку и ничего не пересчитывают. Ручной ввод остаётся
      мастером, решение принимает человек
- [x] Видно, что цену подрезал жёсткий фильтр: сколько ордеров отброшено. Фильтр
      меняет деньги — молчать о нём нельзя
- [x] Хаб без ликвидных ордеров показывается своей формулировкой, а не нулём и не
      «данных нет»: человек должен понимать, что стакан там есть, но он не в рынке
- [x] Возраст истории виден там же, где возраст срезов: сегодняшнего дня в истории
      не бывает никогда, и подпись обязана это отражать
- [x] Тесты на пометки: нормальный спред buy/sell пометки не даёт; цена 1 ISK при
      диапазоне 5900–6200 даёт; потребность 10 000 при обороте 200/сут даёт пометку
      по объёму; отсутствие истории не даёт ни одной пометки и не ломает таблицу

Решения и находки этапа:

- **Очистка переехала из сборщика в чтение — и это оказалось обязательным условием,
  а не улучшением.** Правило §4 срабатывало до записи, и настоящий ордер в мусорной
  книге до базы не доезжал: чинить его коридором было бы нечем. Заодно стало можно
  перебирать пороги без пересбора, а в базе теперь лежит то, что реально отдал ESI.
- **Неторгуемые типы.** По 4 типам из 54 (Chartreuse и Gamboge Cytoserocin, обе формы)
  ESI отвечает 400 «Type not tradable on market!» во всех регионах, хотя стакан по ним
  отдаётся нормально. Считать это ошибкой нельзя: статус сбора навсегда стал бы
  `partial`, а 20 таких ответов в обходе (по 5 токенов лимита ошибок каждый) способны
  прервать цикл. Факт запоминается в `market_history_state.tradable`, перепроверка
  раз в 30 дней.
- **Пороги коридора измерены, а не выдуманы, и оказались асимметричными.** Замер на
  427 книгах и 3917 уровнях: снизу мусор лежит ниже ×0.12 от опоры, сверху честные
  ордера на тонких газах доходят до ×8. Симметричный коридор ×4 резал живое.
  Обоснование асимметрии — цена ошибки: мусор снизу даёт неправильный совет,
  завышенный sell просто проигрывает сравнение.
- **92 книги из 427 состоят из одного уровня.** Правило «×100 от медианы книги» на них
  не работает вовсе: медиане не с чем сравниться. Это ровно те книги, где мусор и живёт.
- **Главная находка — и найдена она в браузере, а не тестами.** По паре, где своей
  истории нет, коридор не применялся вообще, и buy-ордер на 33 ISK по сжатому
  Fullerite-C84 в Rens при реальной цене около 9000 вышел на первое место таблицы
  как «лучший вариант». Пара без истории — это ровно та пара, где мусор и живёт.
  Теперь опора берётся у соседних хабов (`history.borrow`), нужно не меньше двух живых
  соседей, и такой свод помечается заимствованным: как коридор годится, как показания
  оборота — нет. На регрессию поставлены три теста.
- **`/healthz` разделяет сборщики.** Одно «время последнего сбора» показывало бы зелёный
  статус, когда встал один из двух. Возраст истории показывается, но статус не роняет:
  суточный сбор и не обязан быть свежее суток.

Итог проверки на живых данных 19.08.2026: история собрана по 50 типам (10 720 дней,
90 дней на пару), коридор отбрасывает 5.7% уровней, `rens buy Fullerite-C84` отдаёт
«нет ликвидных ордеров» вместо 1 ISK, `rens compressed buy` — 3500 с пометкой
«сделок по вашей цене не было» вместо 33 ISK.

## Этап 12. Новый интерфейс «GasLens Terminal»

Этап косметический по названию и опасный по сути: переписывается вся вёрстка, через
которую человек читает деньги. Правило на весь этап — **ни одно число, ни одна пометка
и ни одно состояние не должны пропасть с экрана**. Контракт формы не меняется вообще:
серверные `_parse_form`, `_build_grid` и `settings.js` обязаны продолжить работать
без правок по существу.

### 12.0 Решения до кода

- [x] **`docs/SPEC.md` §10 переписан.** Прежний текст («минимальное оформление,
      никаких иконок, шрифтов с CDN, анимаций и тем, один `style.css` на 100–150 строк»)
      прямо запрещал то, что нарисовано, и отменён целиком. Новая редакция — семь
      подразделов: что осталось запрещено, правило «ни одно число не пропадает»,

- [x] **Шрифты — вариант (а), решение пользователя от 19.08.2026.** `Archivo`

      `JetBrains Mono` кладутся файлами `woff2` в `app/static/fonts/` и раздаются

## Этап 13. Фильтр «только buy» — сделано 20.08.2026

На экране: чекбокс рядом с работающим «только sell», нарисован неактивным.
В ядре есть `CalcInput.sell_only`, и `build_scenarios` по нему просто не строит
buy-сценарии. Зеркальный фильтр — та же одна строка в цикле, но за ней тянутся
три вопроса: что делать, когда отмечены оба; где хранить настройку; что писать
в пустом состоянии и в сносках.

### 13.0 Решения до кода

- [x] **Два чекбокса, взаимоисключающие, — как в макете.** В макетном JS
      `onSellOnly` гасит `buyOnly` и наоборот. Третий вариант («ни один») — это
      состояние по умолчанию, показываются все строки. Радиокнопки не берём:

## Этап 14. Фильтр «скрыть неликвид» — сделано 20.08.2026

На экране: неактивный чекбокс. Пункт требует отдельного решения, и решение это
не про код: **приложение принципиально ничего не прячет, а показывает
и объясняет.** Фильтр, который молча выкидывает строки, противоречит всему
остальному интерфейсу — значкам-пометкам, сноскам, честному «неликвидная цена».

Отдельно и важно: признак `unconfirmed` считает не ядро, а `routes._history_rows`
по данным истории сделок. Ядро истории не видит вовсе и видеть не должно —
`calculator.py` импортирует только stdlib и `models.py`. Значит, этот фильтр
физически не может жить там, где живёт `sell_only`, и это не мелочь реализации,
а граница: **ядро решает, какие сценарии существуют, интерфейс решает, какие
из них показать.**

### 14.0 Решения до кода

- [x] **Делать — только со счётчиком скрытого.** Под таблицей строка: «скрыто
      N строк: по этим ценам за неделю не торговали». Без неё фильтр
      превращается в способ не заметить, что половина рынка отвалилась
- [x] **Прячем ровно `unconfirmed`** — «сделок по такой цене не было». Ни
      аномальную цену, ни маленький оборот фильтр не трогает: это разные
      пометки про разное, и склеивать их в одну галочку нельзя
- [x] **Строка без истории не скрывается.** Нет данных — это не «неликвид»,
      а «мы не знаем». Скрыть её значит выдать незнание за факт
- [x] **Сводка пересчитывается по видимым строкам.** Иначе «Лучший вариант»
      в полосе итогов будет показывать строку, которой в таблице нет.
      Это самая дорогая часть этапа, см. 14.1

### 14.1 Пересчёт сводки после фильтрации

- [x] В `calculator.py` выделяется чистая функция `summarize(scenarios,
      n_units, compressed_qty) -> tuple[tuple[Scenario, ...], Summary | None]`. Тело
      у неё уже написано — это блок из `build_scenarios`, где считаются
      `delta_pct`, `best`, `worst`, `savings_vs_worst`, `loss_units`,
      `loss_pct`. Сам `build_scenarios` начинает вызывать её вместо inline-кода:
      поведение не меняется ни на число
- [x] `routes.calculate` после отбора видимых строк зовёт `summarize` заново
      и подменяет `result.summary` и `delta_pct` в строках. `Scenario` заморожен,
      поэтому только через `dataclasses.replace` — как это уже делает ядро
- [x] Знаменатель «N из 20» не трогается: 20 — это число ячеек сетки цен,
      а не число построенных сценариев. Числитель — количество видимых строк
- [x] Порядок операций в `calculate` фиксируется и комментируется:
      построить → взять историю → отфильтровать → пересчитать сводку →
      собрать `_row_views`. `_row_views` считает размах ISK и максимальный
      оборот по тому, что ему дали, и после фильтрации это уже другой размах —

### 14.2 Форма, шаблон, счётчик

- [x] Поле `hide_illiquid` в форме; в `CalcInput` оно **не попадает** —

## Этап 17. Панель «Разбор строки» — сделано 20.08.2026

Самый крупный пункт по функционалу — и при этом почти все числа для него уже

глубина стакана, ставка доставки); блок «что смущает» — расшифровку значков
именно этой строки; точку безубыточности этого хаба.

Сейчас на экране этого нет вовсе. Часть содержимого живёт под таблицей
отдельным блоком «Точки безубыточности» — так решено в 12.6 на время,
пока панели нет.

### 17.0 Решения до кода

- [x] **Панель рисует сервер, HTMX её подставляет.** Клик по строке шлёт
      `POST /row-detail` с той же формой плюс ключ строки, ответ — фрагмент,
      который ложится в контейнер под таблицей. Считать те же числа второй раз
      в JS нельзя: математика живёт в ядре, и второй её экземпляр разъедется

- [x] **Ключ строки — тот же `{hub}|{form}|{side}`**, которым уже пользуется

- [x] **Любое изменение параметров закрывает панель.** Внутри неё числа того
      расчёта, который уже не на экране; оставить её открытой значит показывать
      устаревшее рядом со свежим. Так же поступает макет
- [x] **Строка обязана выглядеть нажимаемой** — курсор-рука, подсветка при

      раскрытия либо сама строка получает `tabindex="0"` и обработчик Enter.
      Кликабельная строка без клавиатуры — это элемент, который для части
      людей просто не существует
- [x] **Решён: блок под таблицей убран, число живёт в панели.** Решалось
      в два шага. При сдаче этапа 17 блок был оставлен — проверка этапа

## Этап 18. Тема оформления в настройках аккаунта — сделано 20.08.2026

Тема работает и переключается, но живёт только в `localStorage` — то есть

тёмная, даже если человек давно выбрал светлую.

### 18.0 Решения до кода

- [x] **У вошедшего побеждает аккаунт.** Иначе смысл теряется: настройка,

- [x] **Системная тема (`prefers-color-scheme`) — отдельное решение,

## Этап 19. Переключатель RU / EN (ЗАПРЕТ НА РЕАЛИЗАЦИЮ ДАЖЕ ПРИ ЯВНОМ ЗАПРОСЕ)

Самый большой пункт списка по объёму работы. Английского интерфейса нет вообще:
все тексты зашиты в шаблоны по-русски, и не только в шаблоны — в `routes.py`
живут подписи значков, заметки сетки цен, тексты ошибок разбора формы
и подсказки спарклайна. Пока они там, переключатель нечего переключать.

### 19.0 Решения до кода

- [ ] **Свой словарь, без десятой зависимости.** `Flask-Babel` — это десятая
      строка в `requirements.txt` и цепочка `babel` + `pytz` за ней, ради
      двух языков и статических строк. Стандартный `gettext` без Babel — это
      `.po`/`.mo`, компиляция `msgfmt` и бинарники в репозитории. Предложение:
      два модуля-словаря `app/i18n/ru.py` и `app/i18n/en.py` — плоские
      `dict[str, str]` с короткими ключами-слагами, плюс функция `t(key)`,
      зарегистрированная глобалом Jinja
- [ ] **Язык хранится в cookie, а не в `localStorage`.** Страницу собирает
      сервер, и он обязан знать язык до рендера; `localStorage` на сервер
      не приезжает никогда. Это техническое отличие языка от темы: тему может
      применить CSS на клиенте, язык — нет. Cookie функциональная, баннера
      согласия не требует
- [ ] **У вошедшего язык — такая же настройка аккаунта, как тема** (этап 18):
      колонка, миграция, приоритет аккаунта над cookie
- [ ] **Числа и даты тоже переводятся.** Разделитель разрядов, десятичная
      запятая, формат даты `ДД.ММ.ГГГГ` — всё это часть языка. `formatting.py`
      сейчас жёстко ставит пробел разрядом и точку дробной частью; ему нужен
      параметр локали, а не второй набор функций
- [ ] **Делать в два прохода.** Первый — вынести все русские строки в словарь
      и заменить их вызовами `t()`; на экране при этом не меняется ничего,
      и это проверяется существующими тестами. Второй — написать английский
      словарь и включить переключатель. Смешивать проходы нельзя: первый
      трогает каждый шаблон и половину `routes.py`, и ловить в этом ещё
      и ошибки перевода — гарантированный способ потерять строку

### 19.1 Где лежат тексты

Инвентаризация перед работой — иначе половина строк найдётся уже после
включения английского:

- [ ] `app/templates/index.html`, `partials/results.html`, `partials/prices.html`,
      `partials/icons.html` — подписи, заголовки, сноски
- [ ] `app/routes.py` — тексты ошибок разбора формы, `_grid_notes`,
      `_low_volume_notes`, `title_no_trades`, `title_anomaly`,
      `title_low_volume`, `spark_title`, `liquidity_note`
- [ ] `app/core/calculator.py` — тексты `ValueError`. Ядру словарь не положен
      (оно импортирует только stdlib и `models.py`), поэтому оно бросает
      исключения с машинным кодом, а текст подбирает интерфейс. Это правка
      ядра, и её надо делать аккуратно: тесты ядра ищут эти тексты
- [ ] `app/services/server_status.py` — `label` и `title` чипа состояния
- [ ] `app/auth/views.py` — флеш-сообщения входа и выхода
- [ ] `data/gases.json` — имена газов не переводятся: это имена предметов
      в игре, и они одинаковы на любом языке клиента
- [ ] Имена хабов и структур — тоже не переводятся, по той же причине

### 19.2 Код

- [ ] `app/i18n/__init__.py` с `t(key, **kwargs)`, выбором словаря и падением
      на русский ключ, если строки нет: пустое место на экране хуже, чем
      непереведённая строка
- [ ] Язык определяется один раз на запрос: аккаунт → cookie → `Accept-Language`

- [ ] `<html lang="…">` следует за выбранным языком. Сейчас там жёстко `ru`
- [ ] Кнопки RU / EN перестают быть `disabled`, активная получает

- [ ] Ширины в вёрстке проверяются на английском: `Недостаточно данных` и

### 19.3 Тесты

- [ ] Ключи в `ru.py` и `en.py` совпадают до одного — тест сравнивает множества
- [ ] Ни один шаблон не содержит кириллицы вне словаря (регулярка по файлам

1. **Переключатель RU / EN** — этап 19. Английского интерфейса нет вообще: все

     прежних версий и колонку в базе.

   - **Сводка выделена в чистую функцию `calculator.summarize`** и считается
     дважды: ядром по всем сценариям и интерфейсом по видимым. Без этого
     «Лучший вариант» показывал бы строку, которой в таблице нет. Ширины
     полосок и `Δ` едут туда же — они считаются от размаха видимого.
   - **Фильтр, скрывший всё, объясняется словами**, а не «Недостаточно данных»:
     данные есть, их убрала галочка.
6. ~~**Фильтр «по одной строке на хаб».**~~ **Сделано 20.08.2026,** этап 15.
   Оставляет лучший сценарий каждого хаба — стоит на машинке, которую завёл
   этап 14. Решения по ходу:
   - **Общая часть обоих фильтров вынесена в `routes._apply_visibility`.**
     Пересчёт сводки, урезание свода истории и подсчёт скрытого — одно и то же
     у обеих галочек, и второй копии этого кода быть не должно.
   - **Порядок галочек зафиксирован: свёртка идёт после «скрыть неликвид».**
     Наоборот хаб остался бы представленным неликвидной строкой, вторая
     галочка убрала бы её, и хаб пропал бы целиком при живой альтернативе.
     Проверено тестом, а не комментарием.
   - **Счётчик свёрнутого — свой, отдельно от счётчика скрытого.** Две галочки
     убирают строки по разным причинам, и одно число на двоих не объяснило бы
     ни одну из них.
   - **Номер в колонке «#» позиционный и после свёртки честно едет вверх.**
     Тесты сравнивают строки без него: иначе ловилось бы место в списке,
     а не содержимое.
7. ~~**Сортировка кликом по заголовку.**~~ **Сделано 20.08.2026,** этап 16.
   Хаб, Цена, Купить, м³, Итого, ISK/юнит; умолчание не тронуто. Решения по ходу:
   - **Сортирует сервер, браузер только записывает выбор.** Клик пишет
     скрытые поля `sort` и `sort_dir` и дёргает `recalc` — обычный путь формы.
     Порядок в JS был бы вторым источником правды и разъехался бы с полосками.
   - **Место в рейтинге отделено от места на экране.** Раньше `rank`,
     `is_best` и `is_odd` выводились из одного индекса; теперь первые два —
     из порядка по ISK/юнит, третий — из порядка показа. Это и было то самое
     место, где этап мог сломаться тихо: подсветилась бы просто верхняя строка.
   - **Размах для полосок берётся из рейтинга, а не из первой и последней
     строки на экране.** После сортировки по другой колонке это разные числа.
   - **Стабилизатор всегда по возрастанию.** При равных ключах вторым идёт
     ISK/юнит, и он не переворачивается вместе с направлением: это не выбор
     пользователя, а способ не дать порядку плясать между запросами.
   - **Стрелка — глифом из CSS**, как уже сделано у раскрывашки сносок.
     Первая попытка записать её escape-последовательностью `\25be` дала
     в файле управляющий символ; проверено в браузере, а не на глаз.
8. ~~**Панель «Разбор строки» по клику на строку.**~~ **Сделано 20.08.2026,**
   этап 17. Оказался не самым дорогим пунктом: все числа уже считались, нужен
   был способ показать их по одной строке. Решения по ходу:
   - **Панель собирает тот же `_row_views`, что рисует таблицу.** Не «те же
     формулы», а буквально те же значения: `/row-detail` проходит тот же путь,
     что `/calculate`, и берёт из результата одну строку по ключу. Сверено
     тестом, который сравнивает числа панели с числами строки таблицы.
   - **Ключ строки — уже существующий `{hub}|{form}|{side}`.** Он же теперь
     лежит в `_row_view` под ключом `key` и уезжает в `data`-атрибут строки.
   - **Панель живёт внутри ответа `/calculate`.** Отсюда бесплатно берётся
     требование «любое изменение параметров закрывает панель»: блок результата
     приезжает заново, и панель в нём пустая. Отдельного кода на это не нужно.
   - **Блок «Точки безубыточности» под таблицей оставлен.** Предложение было
     перенести его в панель целиком, но проверка этапа требует, чтобы ни одно
     число не пропало с экрана, а в панели оно видно только по клику и только
     по одному хабу. Дублирование тут осмысленное: под таблицей — обзор,
     в панели — контекст своего хаба.
   - **Строка доступна с клавиатуры** через `tabindex="0"` и `keyup[Enter]`
     в `hx-trigger` — декларативно, без единой строчки JS.
9. ~~**Портрет персонажа** вместо буквы в кружке: внешняя картинка
   с `images.evetech.net`.~~ **Сделано 20.08.2026.** Пункт упирался в правило
   «никаких внешних запросов в рантайме», записанное в `CLAUDE.md`. Правило
   оказалось неверно сформулированным и в тот же день отменено: приложение —
   веб-сервис и живёт в интернете, задача не обрезать обращения к чужим
   сервисам, а держать их редкими и считаными (`CLAUDE.md`, «Внешние запросы»).
   Портрет под это подходит: один запрос на загрузку страницы, только
   у вошедшего, дальше картинку держит кэш браузера. Как сделано:
   - **буква в кружке не заменяется, а остаётся под портретом.** Видна, пока
     картинка грузится, и остаётся, если картинка не пришла; битая картинка
     убирается, чтобы на месте аватара не висел значок обрыва. Это и есть
     третье правило раздела: внешний адрес не имеет права сломать страницу;
   - **у анонима внешних адресов нет** — показывать ему нечего;
   - **есть выключатель `CHARACTER_PORTRAITS`** — для закрытого контура и для
     тех, кто не хочет отдавать этот запрос наружу;
   - приложение за картинкой не ходит и не кэширует её: в HTML уходит адрес,
     тянет браузер. Цена названа прямо — CCP видит запрос браузера вошедшего.
10. ~~**Тема оформления в настройках аккаунта.**~~ **Сделано 20.08.2026,**
    этап 18. Решения по ходу:
    - **Запрос кнопки темы разведён с общим сохранением настроек.** `save`
      считает незаполненное поле стёртым — на этом стоит сброс настроек пустой
      формой, — и запрос из одного поля `theme` стёр бы человеку всё остальное.
      Отдельная `save_theme` и отдельная ветка в `/settings/save`; обе стороны
      закрыты тестами: тема не сносит настройки, настройки не сносят тему.
    - **У анонима атрибута `data-theme` в разметке больше нет вовсе.** Раньше
      в `<html>` стояло жёсткое `data-theme="dark"`; теперь атрибут появляется,
      только когда тему знает сервер, а скрипт в `<head>` ставит его из
      `localStorage`, если сервер промолчал. Тёмная при этом никуда не делась —
      она в `:root`, и страница до выполнения скрипта не «никакая». Тест на
      умолчание переписан под это: он проверяет палитру в CSS, а не атрибут.
    - **`aria-pressed` синхронизируется в двух местах.** Сервер знает тему
      вошедшего и ставит атрибут сразу; у анонима сервер не знает ничего,
      и значение поправляет тот же JS, что применяет тему.
    - **Системная тема не трогалась.** `prefers-color-scheme` меняет вид
      приложения при первом заходе — это отдельное решение, а не хвост этапа.

## Отложено

Не делать без отдельной просьбы:

- **Развёртывание на боевом хостинге целиком**: прод-СУБД и миграции на ней,
  waitress под nginx, cron на сервере, секреты в окружении, инструкция по
  установке на Linux. Отдельная задача со своим этапом, а не хвост версии 0.1.0
- Прогон набора тестов на Postgres и MariaDB — часть той же задачи: локально
  разработка идёт на SQLite
- Раздельный расчёт для нескольких газов сразу
- Split-sourcing: набрать часть партии в одном хабе, часть в другом
- Графики цен и истории сделок: данные появятся на этапе 11, интерфейса к ним
  по-прежнему не будет
- Рынки игровых структур: требует scope и докинг-доступа, а мы просим пустой scope
- Разная периодичность сбора для ходовых и редких газов
- Учёт числа курьерских контрактов при лимите объёма на контракт
- Именованные пресеты настроек поверх аккаунта
- **Привести нейминг к единому стандарту.** 19.08.2026 продукт переименован
  в GasLens by EveCraft: title, README, CLAUDE.md и User-Agent для ESI уже говорят
  новым именем. Старое имя осталось там, где оно завязано на файловую систему
  и на слаг репозитория, а их переименование — отдельное решение:
  - `README.md` — `git clone .../EveGAS_calc.git`, `cd EveGAS_calc`, `/srv/EveGAS_calc`
    и `C:\path\to\EveGAS_calc` в строках cron и Планировщика;
  - `CLAUDE.md` — корень дерева проекта `EveGAS_calc/`;
  - имя файла дев-базы `var/evegas_dev.sqlite3` (`app/config.py`);
  - имя каталога разработки на машине.

  Делать это имеет смысл одним заходом и **после** переименования репозитория
  на GitHub, иначе инструкция в README будет вести на несуществующий адрес.
  Проверить заодно `.gitignore`, `alembic.ini` и `.claude/launch.json` на предмет
  захардкоженных путей.
