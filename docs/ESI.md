# ESI.md — интеграция с API EVE Online

Подтяжка цен — **вспомогательная** функция. Приложение обязано полноценно работать
при полностью ручном вводе и при недоступном ESI. Ничего не должно ломаться, если
этот модуль отключить.

---

## 1. Что нужно и сколько это стоит

**С версии 0.1.0 пользователь к ESI не обращается вообще.** Цены собирает один
фоновый сборщик по расписанию, приложение читает готовые срезы из базы. Причина
простая: при подтяжке по кнопке нагрузка на ESI росла пропорционально числу
пользователей, и на второй сотне это привело бы к бану.

Полный обход сборщика:

```
27 газов × 2 формы (сырой + сжатый) × 5 регионов = 270 запросов
```

Каждый запрос с фильтром по типу, ответ маленький. Периодичность по умолчанию —
30 минут; обоснование и расчёт бюджета токенов ниже, в разделе про рейт-лимит.
Это единственное место в проекте, ради которого подключён async.

---

## 2. Эндпоинт

```
GET https://esi.evetech.net/markets/{region_id}/orders/
    ?type_id={type_id}
    &order_type=all
```

Авторизация не нужна — эндпоинт публичный. SSO в проекте не используется вообще.

### Обязательные заголовки

```python
ESI_HEADERS = {
    "User-Agent": "EveGAS_calc/0.0.1 (+https://github.com/USER/EveGAS_calc; contact@example.com)",
    "X-Compatibility-Date": "2026-08-13",
    "Accept": "application/json",
}
```

Оба заголовка обязательны, не опциональны:

- **User-Agent** должен быть осмысленным и содержать контакт. Рейт-лимит на этот эндпоинт включён с 24 февраля 2026, и в первую очередь под него попадают клиенты с безликими UA вроде `python-httpx/0.27`. Вынеси значение в `config.py`, чтобы тот, кто развернёт проект у себя, подставил свой контакт.
- **X-Compatibility-Date** фиксирует поведение API на дату, когда клиент был написан. Без него API может тихо поменять формат ответа.

**Дата не должна быть в будущем.** ESI сравнивает её со своим текущим днём **по UTC-11**
и на дату «сегодня по Москве» отвечает `400 Compatibility date is in the future`
почти полсуток. Проверено живым запросом 2026-08-14: с `2026-08-14` — 400,
с `2026-08-13` — 200. Ставь дату вчерашнего дня либо ту, на которую клиент
реально написан и проверен.

### Ответ

Массив объектов:

```json
{
  "order_id": 4623824223,
  "type_id": 62406,
  "location_id": 60003760,
  "system_id": 30000142,
  "is_buy_order": false,
  "price": 2750.0,
  "volume_remain": 12000,
  "volume_total": 50000,
  "min_volume": 1,
  "range": "region",
  "duration": 90,
  "issued": "2026-08-14T05:12:25Z"
}
```

### Пагинация

Заголовок `X-Pages`. С фильтром по одному `type_id` почти всегда одна страница,
но обработать несколько всё равно надо — молча брать только первую нельзя.

### Кэш

Ответ кэшируется на стороне ESI 5 минут. Соблюдай заголовок `expires`, свой кэш держи
не агрессивнее. Обход кэша CCP прямым текстом называет поводом для бана.

### Рейт-лимит: сколько нам можно

Проверено по документации CCP 17.08.2026. Лимит **токенный**, а не «запросов в секунду».

| Что | Значение |
|---|---|
| Окно | 15 минут, плавающее: потраченные токены возвращаются через 15 минут |
| Бюджет группы `market-order` | **12 000 токенов** |
| Ответ 2XX | 2 токена |
| Ответ 3XX (в том числе `304`) | **1 токен** |
| Ответ 4XX | 5 токенов |
| Ответ 5XX | 0 токенов |
| Остаток | заголовок `X-Ratelimit-Remaining` |
| Бюджет исчерпан | `429` и заголовок `Retry-After` в секундах |

Лимит на `/markets/{region_id}/orders/` включён 24 февраля 2026. По словам CCP,
99% приложений укладываются в 1000 токенов за 15 минут.

**Наша арифметика.** Полный обход — 27 газов × 2 формы × 5 хабов = **270 запросов**:

```
все ответы свежие (2XX):  270 × 2 = 540 токенов
все ответы 304:           270 × 1 = 270 токенов
```

При обходе раз в 30 минут в любое 15-минутное окно попадает максимум один обход,
то есть **540 токенов из 12 000 — 4.5% бюджета**. Даже обход каждые 5 минут дал бы
13.5%, но смысла в нём нет: ESI всё равно отдаёт кэш пятиминутной давности.

**Почему запрашиваем по одному type_id, а не регион целиком.** Соблазн взять весь
стакан региона и отфильтровать у себя выглядит экономнее — 5 запросов вместо 270.
На деле полный стакан The Forge это сотни страниц, каждая по 2 токена: один регион
обошёлся бы дороже, чем все 270 наших запросов вместе. Фильтр по типу — дешёвый путь.

### Лимит ошибок

Отдельный от рейт-лимита механизм, свои заголовки:

- `X-ESI-Error-Limit-Remain` — сколько ошибок осталось в текущем окне;
- `X-ESI-Error-Limit-Reset` — секунд до обнуления счётчика.

Когда лимит исчерпан, ESI **отбрасывает все запросы** до конца окна. Сборщик обязан
следить за этими заголовками и останавливать цикл заранее, а не упираться в стену.

### Условные запросы

Заголовок `ETag` в ответе, `If-None-Match` в следующем запросе, `304` если ничего
не изменилось. Это не только вежливость: `304` стоит вдвое дешевле обычного ответа
и не тратит трафик на неизменившийся стакан.

**`304` означает «твоя копия актуальна», а не «данных нет».** Лестницу переписывать
нечем, но время сбора у сохранённого среза обязано сдвинуться на сейчас: данные
только что подтверждены. Иначе срез навсегда остаётся с датой первой загрузки,
и приложение показывает «собраны сутки назад» с предупреждением об устаревании
на данных, которые ESI подтвердил минуту назад. Срок годности из ответа `304`
тоже применяется — без него следующий цикл пойдёт за этим срезом впустую.

### Кто платит за наши запросы

Бюджет считается на пару «группа лимита / ApplicationID / CharacterID». Как именно
бакетируются **неавторизованные** запросы — по IP, по User-Agent или иначе, —
в документации не сказано, и выдумывать это не нужно. Практический вывод один:
осмысленный User-Agent обязателен, а расчёт бюджета вести по худшему случаю,
считая, что бакет у нас общий на всё приложение.

### Ошибки

- 5xx — до 2 ретраев с экспоненциальной паузой.
- 420 / 429 — не ретраить, вернуть понятную ошибку пользователю.
- Таймаут 15 секунд.
- `asyncio.gather(..., return_exceptions=True)` — падение одного хаба не должно ронять остальные девять запросов. Хаб помечается как «данные не получены», остальные считаются.

## 3. Разбор стакана — самая тонкая часть проекта

Здесь легче всего тихо ошибиться. Читай внимательно.

### 3.1 Sell-ордера

Берём только ордера с `location_id == station_id` целевого хаба.

Sell-ордера привязаны к станции, поле `range` для них смысла не имеет.
Ордера в других станциях того же региона — это другой рынок, они нам не интересны.

```python
sells = [o for o in orders
         if not o["is_buy_order"] and o["location_id"] == hub.station_id]
sells.sort(key=lambda o: o["price"])
```

### 3.2 Buy-ордера — внимание

Buy-ордер имеет **радиус действия** (`range`): `station`, `solarsystem`,
`1`, `2`, `3`, `4`, `5`, `10`, `20`, `30`, `40`, `region`.

Ордер, выставленный в соседней системе с радиусом `region`, **реально конкурирует
с тобой в Jita 4-4**. Если отфильтровать buy-ордера так же, как sell — только по
`location_id` — получишь заниженный top buy и посоветуешь выставиться ниже рынка.

**Принятое упрощение** (реализуем именно так):

```python
buys = [o for o in orders
        if o["is_buy_order"] and (
            o["range"] == "region"
            or o["system_id"] == hub.system_id
        )]
buys.sort(key=lambda o: o["price"], reverse=True)
```

То есть берём: все региональные ордера плюс любые ордера из системы хаба.

**Известная слепая зона:** ордера с числовым радиусом (`5`, `10`, `20`...), выставленные
в соседних системах и дотягивающиеся до хаба, мы не увидим. Точный учёт требует расчёта
числа прыжков между системами, а для этого нужна карта из SDE — а SDE мы намеренно
не тянем в рантайм. Это осознанный компромисс.

**Обязательно** отрази его в интерфейсе одной строкой мелким шрифтом под сеткой цен:
«Цены buy могут быть занижены — не учитываются ордера с радиусом в прыжках из соседних систем».

### 3.3 Ордера из игровых структур

Ордера из Upwell-структур (торговые Keepstar рядом с Jita и т.п.), кроме ranged,
в региональную выдачу **не попадают вообще**. Получить их можно только через
авторизованный эндпоинт с докинг-доступом.

Мы их не получаем. Это ограничение, а не баг. Упомянуть в README.

## 4. Какую цену возвращать

**Не лучшую цену.** Минимальный sell в Rens может быть на 12 юнитов при потребности в 50 000.

Считаем средневзвешенную по нужному объёму (VWAP), проходя по книге:

```python
def vwap(orders: list[dict], needed: int) -> tuple[float | None, int]:
    """
    Идёт по отсортированной книге, набирая needed юнитов.
    Возвращает (средневзвешенная цена, сколько удалось набрать).
    Если набрано меньше needed — цена всё равно считается по набранному,
    а вызывающий код обязан показать предупреждение о глубине.
    """
```

Возвращаем наверх три вещи: **цену**, **доступное количество**, **флаг нехватки глубины**.

Количество для VWAP:

- сырой газ → `N`
- сжатый газ → `ceil(N / eta)`

То есть глубина проверяется под реальную потребность, а не под абстрактную единицу.

### Отсечение выбросов

Перед расчётом убрать явный мусор:

- ордера с `volume_remain <= 0`;
- ордера, чья цена отличается от медианы книги больше чем в 100 раз (продажа юнита за 0.01 ISK и «стены» по конским ценам);
- для buy-ордеров — учитывать `min_volume`: ордер с `min_volume` больше нужного количества исполнить нельзя.

Отсечение делать по медиане, а не по среднему — среднее сам выброс и утаскивает.

## 5. Структура модулей

```
app/services/esi.py        только HTTP: заголовки, ретраи, пагинация, gather
app/services/orderbook.py  чистые функции разбора: фильтрация, выбросы, vwap
app/services/cache.py      dict {(region_id, type_id): (данные, expires_at)}
```

`orderbook.py` не должен ничего знать про HTTP — на вход список словарей, на выход
цифры. Так его можно покрыть тестами на фикстурах без единого сетевого запроса.
Фикстуры положи в `tests/fixtures/orders_*.json`.

---

## 6. Что тестировать обязательно

- VWAP по книге из нескольких ордеров, включая случай нехватки глубины.
- Что buy-ордер с `range: "region"` из чужой системы **попадает** в выборку.
- Что sell-ордер из другой станции того же региона **не попадает**.
- Что ордер с ценой 0.01 при медиане 3000 отбрасывается.
- Что падение одного региона не ломает остальные (мок с исключением в `gather`).
