# ESI.md — интеграция с API EVE Online

Подтяжка цен — **вспомогательная** функция. Приложение обязано полноценно работать
при полностью ручном вводе и при недоступном ESI. Ничего не должно ломаться, если
этот модуль отключить.

---

## 1. Что нужно и сколько это стоит

**С версии 0.1.0 пользователь к ESI не обращается вообще.** Цены собирает один
фоновый сборщик по расписанию, приложение читает готовые срезы из базы. Причина
простая: при подтяжке по кнопке нагрузка на ESI росла пропорционально числу
пользователей, и на второй сотне это привело бы к бану.

Полный обход сборщика:

```
27 газов × 2 формы (сырой + сжатый) × 5 регионов = 270 запросов
```

Каждый запрос с фильтром по типу, ответ маленький. Периодичность по умолчанию —
30 минут; обоснование и расчёт бюджета токенов ниже, в разделе про рейт-лимит.
Это единственное место в проекте, ради которого подключён async.

Сборщиков два, и путать их не надо. Первый ходит за **стаканом** — что выставлено
прямо сейчас; он описан в §2 и бегает каждые 30 минут. Второй ходит за **историей
сделок** — по чему рынок реально торговал; он описан в §5, обновляется раз в сутки
и стоит те же 270 запросов, но один раз в день.

## 2. Эндпоинт

```
GET https://esi.evetech.net/markets/{region_id}/orders/
    ?type_id={type_id}
    &order_type=all
```

Авторизация не нужна — эндпоинт публичный. SSO в проекте не используется вообще.

### Обязательные заголовки

```python
ESI_HEADERS = {
    "User-Agent": "EveGAS_calc/{version} (+https://github.com/USER/EveGAS_calc; contact@example.com)",
    "X-Compatibility-Date": "2026-08-13",
    "Accept": "application/json",
}
```

Оба заголовка обязательны, не опциональны:

- **User-Agent** должен быть осмысленным и содержать контакт. Рейт-лимит на этот эндпоинт включён с 24 февраля 2026, и в первую очередь под него попадают клиенты с безликими UA вроде `python-httpx/0.27`. Вынеси значение в `config.py`, чтобы тот, кто развернёт проект у себя, подставил свой контакт. Номер версии в строке не пишется руками: на месте `{version}` приложение подставляет `__version__` из `app/version.py`.
- **X-Compatibility-Date** фиксирует поведение API на дату, когда клиент был написан. Без него API может тихо поменять формат ответа.

**Дата не должна быть в будущем.** ESI сравнивает её со своим текущим днём **по UTC-11**
и на дату «сегодня по Москве» отвечает `400 Compatibility date is in the future`
почти полсуток. Проверено живым запросом 2026-08-14: с `2026-08-14` — 400,
с `2026-08-13` — 200. Ставь дату вчерашнего дня либо ту, на которую клиент
реально написан и проверен.

### Ответ

Массив объектов:

```json
{
  "order_id": 4623824223,
  "type_id": 62406,
  "location_id": 60003760,
  "system_id": 30000142,
  "is_buy_order": false,
  "price": 2750.0,
  "volume_remain": 12000,
  "volume_total": 50000,
  "min_volume": 1,
  "range": "region",
  "duration": 90,
  "issued": "2026-08-14T05:12:25Z"
}
```

### Пагинация

Заголовок `X-Pages`. С фильтром по одному `type_id` почти всегда одна страница,
но обработать несколько всё равно надо — молча брать только первую нельзя.

### Кэш

Ответ кэшируется на стороне ESI 5 минут. Соблюдай заголовок `expires`, свой кэш держи
не агрессивнее. Обход кэша CCP прямым текстом называет поводом для бана.

### Рейт-лимит: сколько нам можно

Проверено по документации CCP 17.08.2026. Лимит **токенный**, а не «запросов в секунду».

| Что | Значение |
|---|---|
| Окно | 15 минут, плавающее: потраченные токены возвращаются через 15 минут |
| Бюджет группы `market-order` | **12 000 токенов** |
| Ответ 2XX | 2 токена |
| Ответ 3XX (в том числе `304`) | **1 токен** |
| Ответ 4XX | 5 токенов |
| Ответ 5XX | 0 токенов |
| Остаток | заголовок `X-Ratelimit-Remaining` |
| Бюджет исчерпан | `429` и заголовок `Retry-After` в секундах |

Лимит на `/markets/{region_id}/orders/` включён 24 февраля 2026. По словам CCP,
99% приложений укладываются в 1000 токенов за 15 минут.

**Наша арифметика.** Полный обход — 27 газов × 2 формы × 5 хабов = **270 запросов**:

```
все ответы свежие (2XX):  270 × 2 = 540 токенов
все ответы 304:           270 × 1 = 270 токенов
```

При обходе раз в 30 минут в любое 15-минутное окно попадает максимум один обход,
то есть **540 токенов из 12 000 — 4.5% бюджета**. Даже обход каждые 5 минут дал бы
13.5%, но смысла в нём нет: ESI всё равно отдаёт кэш пятиминутной давности.

**Почему запрашиваем по одному type_id, а не регион целиком.** Соблазн взять весь
стакан региона и отфильтровать у себя выглядит экономнее — 5 запросов вместо 270.
На деле полный стакан The Forge это сотни страниц, каждая по 2 токена: один регион
обошёлся бы дороже, чем все 270 наших запросов вместе. Фильтр по типу — дешёвый путь.

### Лимит ошибок

Отдельный от рейт-лимита механизм, свои заголовки:

- `X-ESI-Error-Limit-Remain` — сколько ошибок осталось в текущем окне;
- `X-ESI-Error-Limit-Reset` — секунд до обнуления счётчика.

Когда лимит исчерпан, ESI **отбрасывает все запросы** до конца окна. Сборщик обязан
следить за этими заголовками и останавливать цикл заранее, а не упираться в стену.

### Условные запросы

Заголовок `ETag` в ответе, `If-None-Match` в следующем запросе, `304` если ничего
не изменилось. Это не только вежливость: `304` стоит вдвое дешевле обычного ответа
и не тратит трафик на неизменившийся стакан.

**`304` означает «твоя копия актуальна», а не «данных нет».** Лестницу переписывать
нечем, но время сбора у сохранённого среза обязано сдвинуться на сейчас: данные
только что подтверждены. Иначе срез навсегда остаётся с датой первой загрузки,
и приложение показывает «собраны сутки назад» с предупреждением об устаревании
на данных, которые ESI подтвердил минуту назад. Срок годности из ответа `304`
тоже применяется — без него следующий цикл пойдёт за этим срезом впустую.

### Кто платит за наши запросы

Бюджет считается на пару «группа лимита / ApplicationID / CharacterID». Как именно
бакетируются **неавторизованные** запросы — по IP, по User-Agent или иначе, —
в документации не сказано, и выдумывать это не нужно. Практический вывод один:
осмысленный User-Agent обязателен, а расчёт бюджета вести по худшему случаю,
считая, что бакет у нас общий на всё приложение.

### Ошибки

- 5xx — до 2 ретраев с экспоненциальной паузой.
- 420 / 429 — не ретраить, вернуть понятную ошибку пользователю.
- Таймаут 15 секунд.
- `asyncio.gather(..., return_exceptions=True)` — падение одного хаба не должно ронять остальные девять запросов. Хаб помечается как «данные не получены», остальные считаются.

## 3. Разбор стакана — самая тонкая часть проекта

Здесь легче всего тихо ошибиться. Читай внимательно.

### 3.1 Sell-ордера

Берём только ордера с `location_id == station_id` целевого хаба.

Sell-ордера привязаны к станции, поле `range` для них смысла не имеет.
Ордера в других станциях того же региона — это другой рынок, они нам не интересны.

```python
sells = [o for o in orders
         if not o["is_buy_order"] and o["location_id"] == hub.station_id]
sells.sort(key=lambda o: o["price"])
```

### 3.2 Buy-ордера — внимание

Buy-ордер имеет **радиус действия** (`range`): `station`, `solarsystem`,
`1`, `2`, `3`, `4`, `5`, `10`, `20`, `30`, `40`, `region`.

Ордер, выставленный в соседней системе с радиусом `region`, **реально конкурирует
с тобой в Jita 4-4**. Если отфильтровать buy-ордера так же, как sell — только по
`location_id` — получишь заниженный top buy и посоветуешь выставиться ниже рынка.

**Принятое упрощение** (реализуем именно так):

```python
buys = [o for o in orders
        if o["is_buy_order"] and (
            o["range"] == "region"
            or o["system_id"] == hub.system_id
        )]
buys.sort(key=lambda o: o["price"], reverse=True)
```

То есть берём: все региональные ордера плюс любые ордера из системы хаба.

**Известная слепая зона:** ордера с числовым радиусом (`5`, `10`, `20`...), выставленные
в соседних системах и дотягивающиеся до хаба, мы не увидим. Точный учёт требует расчёта
числа прыжков между системами, а для этого нужна карта из SDE — а SDE мы намеренно
не тянем в рантайм. Это осознанный компромисс.

**Обязательно** отрази его в интерфейсе одной строкой мелким шрифтом под сеткой цен:
«Цены buy могут быть занижены — не учитываются ордера с радиусом в прыжках из соседних систем».

### 3.3 Ордера из игровых структур

Ордера из Upwell-структур (торговые Keepstar рядом с Jita и т.п.), кроме ranged,
в региональную выдачу **не попадают вообще**. Получить их можно только через
авторизованный эндпоинт с докинг-доступом.

Мы их не получаем. Это ограничение, а не баг. Упомянуть в README.

## 4. Какую цену возвращать

**Не лучшую цену.** Минимальный sell в Rens может быть на 12 юнитов при потребности в 50 000.

Считаем средневзвешенную по нужному объёму (VWAP), проходя по книге:

```python
def vwap(orders: list[dict], needed: int) -> tuple[float | None, int]:
    """
    Идёт по отсортированной книге, набирая needed юнитов.
    Возвращает (средневзвешенная цена, сколько удалось набрать).
    Если набрано меньше needed — цена всё равно считается по набранному,
    а вызывающий код обязан показать предупреждение о глубине.
    """
```

Возвращаем наверх три вещи: **цену**, **доступное количество**, **флаг нехватки глубины**.

Количество для VWAP:

- сырой газ → `N`
- сжатый газ → `ceil(N / eta)`

То есть глубина проверяется под реальную потребность, а не под абстрактную единицу.

### Отсечение выбросов

Перед расчётом убрать явный мусор:

- ордера с `volume_remain <= 0`;
- ордера, чья цена отличается от медианы книги больше чем в 100 раз (продажа юнита за 0.01 ISK и «стены» по конским ценам);
- для buy-ордеров — учитывать `min_volume`: ордер с `min_volume` больше нужного количества исполнить нельзя.

Отсечение делать по медиане, а не по среднему — среднее сам выброс и утаскивает.

У правила есть предел: опора взята из самой книги. Пока мусор в меньшинстве, медиана
держится за настоящие ордера и всё работает. Когда мусора больше половины — медиана
переезжает к нему, и правило выбрасывает уже настоящий ордер (проверено, таблица в §5.4).
Поэтому там, где есть история сделок, опора берётся снаружи и **это правило заменяется**
коридором вокруг цены реальных сделок, §5.4. Без истории оно остаётся единственным.

## 5. История сделок: чем рынок подтверждает цену

Стакан — это хотелки продавцов. Ордер можно выставить любой: за 0.01 ISK на дюжину
юнитов, за миллион «на дурака», стеной на объём, который никто никогда не возьмёт.
История сделок — то, что рынок **реально принял**: по каким ценам газ действительно
переходил из рук в руки и сколько его при этом ушло.

**Цель у истории ровно одна: отсекать цены, по которым газ на самом деле не торгуется.**
Не графики, не витрины, не аналитика. Приложение отвечает на вопрос «какой газ и где
сегодня выгоднее купить», и единственное, чем история этому помогает, — не даёт мусорному
ордеру попасть в расчёт. Правила применения — в §5.4 и §5.5, запреты — в §5.6.

Живой случай, ради которого всё и затевается: в Rens buy-ордер на **1 ISK** при реальной
цене газа 6000 и выше.

### 5.1 Эндпоинт

```
GET https://esi.evetech.net/markets/{region_id}/history/
    ?type_id={type_id}
```

Публичный, авторизация не нужна. Заголовки те же обязательные, что и у `/orders/` (§2).

Проверено живым запросом 18.08.2026 по `region_id=10000002`, `type_id=62406`:
200 OK, массив из **412 записей** — история за тринадцать месяцев в одном ответе.
Копить её самим не нужно.

### 5.2 Что в ответе и чего в нём нет

```json
{
  "date": "2026-08-17",
  "average": 30210.0,
  "highest": 31900.0,
  "lowest": 30210.0,
  "order_count": 20,
  "volume": 122758
}
```

Одна запись — одни календарные сутки по UTC. `volume` — сколько юнитов за день
реально сменило владельца, `highest` и `lowest` — крайние цены состоявшихся сделок.
`order_count` спека описывает как «Total number of orders happened that day».

**Чем взвешена `average`, спека не пишет.** Не додумывать: «volume-weighted average»
в схеме не сказано ни слова. Эмпирически на тех же 412 днях она всегда лежит между
`lowest` и `highest`, а с их серединой совпадает только в 33 случаях — то есть это
не среднее крайних, но и утверждать, что это VWAP по объёму, оснований нет.

Чего в этих данных нет — важнее того, что есть:

- **Разбивки по станциям.** Только регион целиком. Для The Forge это «Jita плюс всё
  остальное»; отделить сделки, прошедшие в 4-4, нельзя.
- **Разделения buy и sell.** Средняя мешает сделки, закрытые об sell-ордера, и сделки,
  закрытые об buy-ордера. Это не «цена покупки» и не «цена продажи», а цена вообще.
- **Внутридневных данных.** Ровно одно значение на сутки, никакого скользящего окна
  «за последние 24 часа».
- **Отдельных транзакций.** Они есть только в `/characters/{id}/wallet/transactions/` —
  это чужой кошелёк, нужен scope и вход персонажа. Нам туда нельзя (§5.6).

**История региональная — храним её по `region_id`, а не по ключу хаба.** Сейчас пять
наших хабов лежат в пяти разных регионах, и одно однозначно отображается в другое.
Но это свойство нашего списка хабов, а не API: появится второй хаб в том же регионе —
история у них будет общая, одна на двоих.

### 5.3 Ритм и цена запроса

**Эндпоинт истории не входит ни в одну группу рейт-лимита.** Проверено сравнением
заголовков двух ответов 18.08.2026:

| Заголовок | `/orders/` | `/history/` |
|---|---|---|
| `X-Ratelimit-Group` | `market-order` | **отсутствует** |
| `X-Ratelimit-Limit` | `12000/15m` | отсутствует |
| `Expires` | +5 минут | `Wed, 19 Aug 2026 11:05:00 GMT` |
| `Last-Modified` | — | `Tue, 18 Aug 2026 11:25:54 GMT` |
| `ETag` | сильный | слабый (`W/"..."`) |

Данные обновляются раз в сутки: в описании эндпоинта прямым текстом сказано
«This route expires daily at 11:05». Отсюда весь режим сбора:

- ходить **один раз в сутки, после 11:05 UTC**; чаще — бессмысленно, ответ не изменится;
- за один заход те же **270 целей** (27 газов × 2 формы × 5 регионов), то есть 270
  запросов в сутки против примерно 13 000 у сборщика стакана. На фоне основного
  сбора это погрешность;
- лимита ошибок (§2) это не отменяет: заголовки `X-ESI-Error-Limit-*` приходят и здесь,
  следить за ними обязательно;
- условные запросы работают: слабый `ETag` в `If-None-Match` плюс `If-Modified-Since`
  по `Last-Modified`. На `304` данные не переписываем, но время проверки сдвигаем —
  ровно по тому же правилу, что и для срезов стакана (§2).

Отсутствие рейт-лимита сегодня не означает разрешения долбить: сутки кэша заданы
самим CCP, и обход этого кэша — тот же повод для бана, что и в §2.

### 5.4 Как мы это используем: опорная цена вместо медианы книги

Правило из §4 — «выбросить ордер, если он отличается от медианы книги больше чем
в 100 раз» — работает, только пока мусор в меньшинстве. Как только мусора больше
половины, медиана переезжает к нему, и правило начинает выбрасывать **настоящий**
ордер. Проверено на живом коде `orderbook.py` 19.08.2026:

| Книга buy-ордеров | Что оставляет фильтр §4 |
|---|---|
| один ордер по 1 ISK, три по 6000 | `6000, 6000, 5900` — верно |
| три ордера по 1 ISK, один по 6000 | `1, 1, 1` — **выброшен настоящий ордер** |

Во второй строке top buy получается 1 ISK, и именно это мы видели в Rens. Дело
не в коэффициенте: любая опора, взятая из самой книги, врёт вместе с книгой.

Поэтому опора берётся снаружи — из истории сделок:

```
P_ref = медиана `average` по последним HISTORY_REFERENCE_DAYS дням, где volume > 0
```

Медиана, а не среднее — по той же причине, что и в §4: один сумасшедший день не должен
утащить опору. Дни с нулевым оборотом выбрасываются: цена дня, в который не было ни одной
сделки, ничего не подтверждает.

Коридор, в котором ордер считается рыночным, — тот же по форме, но вокруг `P_ref`
и **асимметричный**:

```
[ P_ref / HISTORY_BAND_LOW_FACTOR ,  P_ref * HISTORY_BAND_HIGH_FACTOR ]
```

Применяется к обеим сторонам книги: скам-ордер на 1 ISK — это buy, а «стена» по конской
цене — sell. Но пороги у них разные, и это вывод из замера на живых данных (19.08.2026,
`tools/measure_history_band.py`), а не небрежность:

- **снизу строго, ÷4.** Мусор снизу — это неправильный совет. Buy-ордер на 1 ISK делает
  хаб «выгоднейшим местом выставиться», и человек теряет деньги. В замере настоящие
  buy-ордера жались к опорной цене, а весь мусор лежал ниже ×0.12: порог ×0.25 проходит
  между ними с запасом;
- **сверху свободно, ×10.** Завышенный sell к неправильному совету не ведёт — строка
  просто проигрывает сравнение. Зато на тонких газах встречаются честные ордера в 4–8
  опорных цен, и резать их значит прятать реальную ликвидность. Явные «стены» в замере
  начинались с ×9.8 и доходили до ×104.

**Когда история пригодна, коридор заменяет собой правило §4, а не добавляется к нему.**
Оставить оба значило бы сохранить ровно тот случай из таблицы выше, ради которого всё
и делается: медиана мусорной книги выбросит настоящий ордер ещё до того, как до него
доберётся коридор.

Пригодной история считается при двух условиях сразу:

- она свежее `HISTORY_MAX_AGE_DAYS`;
- в окне есть хотя бы три дня с ненулевым оборотом.

Не выполнено — сначала пробуем **запасную опору: тот же тип газа в других регионах**.
Один и тот же газ в разных хабах стоит по-разному, но разница измеряется десятками
процентов, а коридор шире вчетверо снизу и вдесятеро сверху — для отсечения мусора
точности с запасом. Нужно не меньше двух живых соседей: один регион мог сам оказаться
перекошенным. Такой свод помечается заимствованным: как коридор он годится, как
показания — нет, и оборот чужого региона за свой не выдаётся (§5.5).

Почему это не «на всякий случай». Проверено в браузере 19.08.2026: по сжатому
Fullerite-C84 в Rens сделок за неделю не было вовсе, коридор не применился, и buy-ордер
на **33 ISK** при реальной цене около 9000 вышел на первое место таблицы как «лучший
вариант». Пара без своей истории — это ровно та пара, где мусор и живёт.

Не нашлось и соседей — работает старое правило §4, ровно как сегодня. Для редкого газа
в мелком хабе это нормальное состояние, а не авария.

**Если коридор выбросил всю книгу — это и есть ответ.** Откатывать фильтр нельзя:
откат вернёт ровно тот мусор, ради которого он и написан. Хаб показывается как
«ликвидных ордеров нет» — отдельно от «данных нет» (стакан не собран) и отдельно
от «стакан пуст» (ордеров не было вовсе). Пустая книга здесь не ошибка, а честный
ответ: по этой цене никто не торгует.

Обратная сторона: неверные пороги этим способом могут обнулить живой хаб. Поэтому
пороги не выдуманы, а измерены. Замер 19.08.2026 на 427 книгах и 3917 уровнях живого
стакана: коридор отбросил **222 уровня (5.7%)** и обнулил **6 книг** — все шесть
состояли ровно из одного ордера по 1 ISK или 0.01 ISK, включая тот самый buy на
Fullerite-C84 в Rens при опорной цене 8700.

Отдельная находка того же замера: **92 книги состоят из единственного уровня**.
Правило §4 на них не работает вообще — медиане не с чем сравнивать, и ордер
проходит в расчёт как есть, каким бы он ни был. Внешняя опора закрывает и это.

**Сколько ордеров отброшено — показывать.** Фильтр меняет цифру, за которой человек
пришёл; молча менять деньги нельзя.

**Где именно фильтр применяется — при чтении, а не при сборе.** Сегодня очистка живёт
в `ladder_from_orders`, то есть в сборщике: в базу едет уже очищенная лестница. Оставить
так нельзя по двум причинам.

Первая — фатальная. Правило §4 срабатывает **до** записи, и в случае мусорной книги
настоящий ордер до базы просто не доезжает: в Rens в лестницу лягут три уровня по 1 ISK,
а уровень 6000 будет потерян навсегда. Коридор по истории, применённый потом при чтении,
чинить будет уже нечего.

Вторая — прикладная. Коэффициенты придётся подбирать (этап 11.3), а лестница, очищенная
старым коэффициентом, новым уже не переочистится: нужен полный пересбор и ожидание цикла.

Значит, разделение обязанностей меняется так:

| Что | Где делается |
|---|---|
| отбор по станции и радиусу, выброс мёртвых ордеров, сортировка | сборщик, как и сейчас: от объёма и от истории не зависит |
| отсечение выбросов — и по истории, и старое правило §4 | **чтение из базы**, вместе с фильтром по `min_volume` и VWAP |

В базе после этого лежит лестница ровно такой, какой её отдал ESI. Это и правильнее
по сути: база хранит факт, а не наше мнение о нём.

### 5.5 Что из истории видит пользователь

Фильтр из §5.4 работает молча и только с данными сборщика. Этого мало: цену можно
ввести руками, и тогда никакой фильтр её не проверит. Поэтому те же числа выводятся
в таблицу результата — человек должен сам видеть, торгуют по этой цене или нет.

По каждой паре «хаб + форма газа» из истории берутся три вещи:

| Величина | Как считается |
|---|---|
| Опорная цена | `P_ref` из §5.4 — медиана дневных `average` за окно. То же число, что и в фильтре, не второе рядом |
| Диапазон сделок | `min(lowest)` … `max(highest)` по тем же дням |
| Оборот | сумма `volume` за окно и среднесуточное значение |

Диапазон, а не одна цена, — потому что история мешает обе стороны сделки (§5.2).
Buy-ордер честно стоит ниже опорной цены, sell — выше, и сравнивать их с одним
числом значит ловить нормальный спред вместо мусора. Диапазон реальных сделок этот
спред уже в себе содержит.

**Мягкая пометка «цена не подтверждена сделками».** Строка помечается, если её цена
выходит за диапазон шире, чем на `HISTORY_WARN_FACTOR`:

```
цена < min(lowest) / HISTORY_WARN_FACTOR   или   цена > max(highest) * HISTORY_WARN_FACTOR
```

Порогов, таким образом, два, и путать их нельзя:

| Порог | Что делает | К чему применяется |
|---|---|---|
| `HISTORY_BAND_LOW_FACTOR` / `HISTORY_BAND_HIGH_FACTOR` (жёсткий: ÷4 и ×10 от `P_ref`) | выбрасывает ордер из книги | только к лестнице от сборщика |
| `HISTORY_WARN_FACTOR` (мягкий, ×1.5 от диапазона) | помечает строку, ничего не меняя | к любой цене, включая введённую руками |

Ручной ввод остаётся мастером: пометка ничего не пересчитывает и не подменяет.
Она говорит одно — «сделок по такой цене за неделю не было».

**Пометка по объёму.** Отдельная от цены и не менее важная: цена может быть настоящей,
а купить по ней нужное количество всё равно не получится. Сравнивается потребность
именно этой строки с оборотом именно этого типа:

- сырой газ → `N` против оборота сырого;
- сжатый → `ceil(N / eta)` против оборота сжатого.

Сравнивать потребность в сжатом с оборотом сырого — готовая ошибка, оборот у них разный.

| Условие | Смысл |
|---|---|
| потребность больше оборота за всё окно | за неделю столько не продали — набрать нереально |
| потребность больше среднесуточного оборота | рынок должен работать на вас несколько дней |

Оба состояния — пометка строки, а не её удаление. Решает человек: 10 000 юнитов при
обороте 200 в сутки, может быть, и наберутся за две недели, если он готов ждать.
Наше дело — чтобы он не узнал об этом уже после оплаты доставки.

### 5.6 Чего с историей делать нельзя

- **Подставлять `average` в расчёт вместо VWAP по стакану.** Она региональная и мешает
  обе стороны сделки: как цена покупки в конкретном хабе она просто неверна. История —
  только опора для отсечения мусора, цену по-прежнему даёт стакан.
- **Строить на ней витрины: графики цен, «динамику рынка», историю по дням.** Числа
  из §5.5 в таблице — это проверка цены, а не витрина. Всё, что не помогает ответить
  «где сегодня выгоднее купить», — другое приложение.
- **Называть `average` средневзвешенной по объёму.** В схеме этого нет (§5.2).
- **Считать историю свежей.** Данные за вчера появляются только после 11:05 UTC,
  сегодняшнего дня в ней нет вообще. Всё, что показано пользователю на её основе,
  обязано быть подписано датой.
- **Ходить за настоящими транзакциями в `/characters/{id}/wallet/transactions/`.**
  Это требует scope и входа персонажа, а у нас пустой список scope и обязательный
  анонимный доступ. Ограничение принято осознанно.

## 6. Структура модулей

```
app/services/esi.py        только HTTP: заголовки, ретраи, пагинация, gather
app/services/orderbook.py  чистые функции разбора: фильтрация, выбросы, vwap
app/services/prices.py       чтение сохранённых срезов из базы и возраст данных
app/services/history.py      опорная цена и коридор по истории сделок (§5.4)
app/jobs/collect.py          обход хабов по расписанию, запись срезов
app/jobs/collect_history.py  суточный обход истории сделок
```

Кэша в памяти процесса нет с версии 0.1.0: его роль взяла база, и срез живёт
дольше одного запуска.

`orderbook.py` не должен ничего знать про HTTP — на вход список словарей,
на выход цифры. Так его можно покрыть тестами на фикстурах без единого сетевого запроса.
Фикстуры положи в `tests/fixtures/orders_*.json`.

## 7. Что тестировать обязательно

- VWAP по книге из нескольких ордеров, включая случай нехватки глубины.
- Что buy-ордер с `range: "region"` из чужой системы **попадает** в выборку.
- Что sell-ордер из другой станции того же региона **не попадает**.
- Что ордер с ценой 0.01 при медиане 3000 отбрасывается.
- Что падение одного региона не ломает остальные (мок с исключением в `gather`).

По истории сделок (§5.4), когда она появится:

- Опорная цена считается по медиане и игнорирует дни с нулевым оборотом.
- Книга из трёх ордеров по 1 ISK и одного по 6000 при опорной цене 6000 отдаёт
  **6000**, а не 1 — тот самый случай из §5.4, ради которого всё и написано.
- Честное движение рынка вдвое коридором **не** отбрасывается.
- Пустая или протухшая история — работает правило §4, книга не меняется.
- Книга целиком из мусора отдаёт «ликвидных ордеров нет», а не цену мусора.
- Коридор применяется к обеим сторонам: скам-buy и sell-«стена» отсекаются одинаково.
- Мягкая пометка (§5.5) срабатывает на введённой руками цене, когда фильтр к ней
  не применялся вовсе.
- Нормальный спред buy/sell мягкой пометки **не** вызывает: обе цены лежат внутри
  диапазона реальных сделок.
- Потребность в сжатом сравнивается с оборотом сжатого, а не сырого.
