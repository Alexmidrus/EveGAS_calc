# gascalc

Калькулятор выгодности закупки газа в EVE Online.

Сравнивает покупку сырого и сжатого газа по sell- и buy-ордерам в пяти основных
трейд-хабах, с учётом потерь при разжатии и стоимости курьерской доставки.
Ответ — одна таблица, отсортированная по итоговой цене за один полезный юнит.

## Зачем

Газ торгуется в двух формах. Сжатый занимает в 10 раз меньше места, но при разжатии
теряется от 5 до 20% в зависимости от структуры и навыка — то есть покупать его надо
с запасом. Дешевле возить, но дороже покупать. Что выгоднее сегодня, зависит от текущих
цен в конкретном хабе и от того, сколько стоит доставка именно оттуда. Считать это
в голове каждый раз — неудобно.

## Установка

```bash
git clone <repo>
cd gascalc
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp config.example.py config.py
```

В `config.py` укажи свой контакт в `ESI_USER_AGENT` — это требование API EVE Online.

Без `config.py` приложение всё равно запустится — возьмёт значения из `config.example.py`
и напишет об этом предупреждение в лог. Для локальной разработки этого хватает, но к этапу
подтяжки цен свой User-Agent нужен обязательно: безликие попадают под рейт-лимит.

## Запуск

Локально:

```bash
python run.py
```

На хостинге — через waitress, встроенный сервер Flask для продакшена не годится:

```bash
waitress-serve --host=0.0.0.0 --port=8080 --threads=8 --call app:create_app
```

`--call` нужен потому, что `create_app` — фабрика, а не готовый объект приложения.
Потоки нужны из-за подтяжки цен: она держит запрос на время похода в ESI, и на одном
потоке остальные посетители будут ждать. Кэш ESI живёт в памяти процесса, поэтому
несколько процессов (`--processes`) греют его каждый по-своему — при таком трафике
проще держать один процесс с потоками.

Ни Docker, ни база данных, ни Node.js не нужны. Приложение stateless, настройки
пользователя хранятся в браузере.

Перед публикацией в интернет обязательно скопируй `config.example.py` в `config.py`
и подставь свой контакт в `ESI_USER_AGENT`, иначе запросы к ESI попадут под рейт-лимит,
и выключи `DEBUG`.

## Как пользоваться

1. Выбери газ и укажи, сколько сырых юнитов нужно.
2. Задай тип структуры и уровень навыка Gas Decompression Efficiency — от них зависит,
   сколько газа переживёт разжатие.
3. Заполни ставки курьерской доставки в ISK за м³ **отдельно для каждого хаба** —
   маршруты разные, и это сильно влияет на результат.
4. Впиши цены. Можно вручную, можно нажать «Подтянуть цены из ESI» и потом поправить.
5. Смотри таблицу. Верхняя строка — лучший вариант на сейчас.

Таблица пересчитывается сама при изменении любого поля; кнопка «Посчитать» тоже
работает. Галочка «только sell» убирает buy-сценарии: buy-ордер — это заявка,
она может не исполниться, и когда газ нужен сегодня, половина строк только мешает.

## Ограничения

- **Рынки игровых структур не видны.** Ордера из Upwell-структур не попадают в публичную
  выдачу API. Если рядом с хабом стоит торговый Keepstar с газом, калькулятор его не учтёт.
- **Цены buy могут быть занижены.** Не учитываются buy-ордера с радиусом действия
  в прыжках, выставленные в соседних системах. Учитываются региональные ордера
  и ордера из системы самого хаба.
- **Курьерка считается по одной ставке за м³.** Лимит объёма на один контракт
  не моделируется — если объём большой, контрактов физически потребуется несколько.
- **Цена — не лучший ордер, а средневзвешенная на нужный объём.** Минимальный sell может
  быть на десяток юнитов при потребности в десятки тысяч. Если стакана не хватило,
  строка результата помечается и показывает, сколько юнитов там на самом деле.
- Данные из API кэшируются на 5 минут — столько же, сколько кэширует их сам API.
  Кэш живёт в памяти процесса и очищается при перезапуске. Фонового опроса нет:
  запрос уходит только по кнопке.
- **`ESI_COMPATIBILITY_DATE` не должна быть в будущем.** ESI считает текущий день
  по UTC-11 и на завтрашнюю дату отвечает `400`. Подробности — `docs/ESI.md` §2.

## Обновление справочника газов

`data/gases.json` **генерируется** скриптом `tools/build_gases.py` из SDE. Вручную
его не правят: соответствие сжатого типа сырому берётся из `typeMaterials`
(у сжатого газа ровно один материал в количестве 1 — это и есть сырой газ).

Обновлять нужно, только если CCP добавит или переименует типы газа. В рантайме SDE
не используется, зависимостей у скрипта нет — хватает стандартной библиотеки.

```bash
curl -O https://eve-static-data-export.s3-eu-west-1.amazonaws.com/tranquility/sde.zip
```

```bash
python tools/build_gases.py --sde sde.zip --check
```

`--check` ничего не пишет и только показывает расхождения с текущим справочником.
Убедившись, что расхождения ожидаемые, запусти без него:

```bash
python tools/build_gases.py --sde sde.zip
```

Архив (около 107 МБ) распаковывать не нужно, можно указать и путь к распакованному
каталогу. Порядок газов в файле сохраняется, новые типы дописываются в конец.
Любое несоответствие — объёмы не 10:1, не один материал, тип не из группы газов —
это ошибка: скрипт падает и файл не переписывает. После обновления прогони тесты.
