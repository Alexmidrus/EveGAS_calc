# EveGAS_calc

Калькулятор выгодности закупки газа в EVE Online.

Сравнивает покупку сырого и сжатого газа по sell- и buy-ордерам в пяти основных
трейд-хабах, с учётом потерь при разжатии и стоимости курьерской доставки.
Ответ — одна таблица, отсортированная по итоговой цене за один полезный юнит.

## Зачем

Газ торгуется в двух формах. Сжатый занимает в 10 раз меньше места, но при разжатии
теряется от 5 до 20% в зависимости от структуры и навыка — то есть покупать его надо
с запасом. Дешевле возить, но дороже покупать. Что выгоднее сегодня, зависит от текущих
цен в конкретном хабе и от того, сколько стоит доставка именно оттуда. Считать это
в голове каждый раз — неудобно.

## Установка

```bash
git clone https://github.com/Alexmidrus/EveGAS_calc.git
cd EveGAS_calc
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp config.example.py config.py
alembic upgrade head
```

Последняя строка создаёт схему. Приложение не создаёт таблицы само: схема
меняется только миграциями, и в dev это тот же путь, что в prod.

В `config.py` укажи свой контакт в `ESI_USER_AGENT` — это требование API EVE Online.

Без `config.py` приложение всё равно запустится на умолчаниях dev-профиля и напишет
об этом предупреждение в лог. Для локальной разработки этого хватает, но свой
User-Agent нужен обязательно: безликие попадают под рейт-лимит ESI.

## Профили запуска

Профиль выбирается переменной окружения `APP_ENV` и только ей. Значений два:

| | `dev` | `prod` |
|---|---|---|
| Когда | разработка, локальные тесты | боевая работа |
| База | SQLite в `var/`, создаётся сама | MariaDB, MySQL или Postgres |
| `DEBUG` | включён | выключен, включить нельзя |
| Секреты | не требуются | обязательны, только из окружения |
| Порт по умолчанию | 5000 | 8080 |

По умолчанию — `dev`, так что локально ничего задавать не нужно.

Конфигурация собирается тремя слоями, каждый следующий перебивает предыдущий:

```
умолчания профиля  →  config.py  →  переменные окружения
```

Умолчания живут в `app/config.py`, он же источник истины. `config.py` в корне —
локальные правки, в git не попадает. Профиль из `config.py` задать нельзя:
иначе прод-запуск мог бы молча оказаться dev-запуском.

### Переменные окружения

| Переменная | Профиль | Смысл |
|---|---|---|
| `APP_ENV` | оба | `dev` или `prod`, по умолчанию `dev` |
| `SECRET_KEY` | prod, обязательна | подпись сессии, не короче 32 символов |
| `DATABASE_URL` | prod, обязательна | адрес СУБД, SQLite не принимается |
| `ESI_USER_AGENT` | prod, обязателен свой | шаблонное значение роняет запуск |
| `ESI_CLIENT_ID` | для входа | идентификатор приложения из EVE Developers |
| `ESI_CLIENT_SECRET` | для входа | его секрет, только через окружение |
| `SSO_REDIRECT_URI` | для входа | колбэк, посимвольно как у CCP |
| `ESI_COMPATIBILITY_DATE` | оба | дата, на которую написан клиент ESI |
| `ESI_TIMEOUT` | оба | таймаут запроса, секунды |
| `ESI_CACHE_TTL` | оба | кэш ответов, не меньше 300 секунд |
| `HOST`, `PORT`, `DEBUG` | оба | адрес прослушивания и отладчик |

Ключ подписи генерируется так:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

### Что проверяется при старте

Непригодная конфигурация роняет запуск сразу и с внятным текстом — чтобы проблема
всплыла при развёртывании, а не на первом запросе пользователя посреди рабочего дня.
В профиле `prod` это: отсутствующий или короткий `SECRET_KEY`, отсутствующий
`DATABASE_URL`, SQLite в качестве боевой базы, включённый `DEBUG`, шаблонный
`ESI_USER_AGENT`. В обоих профилях проверяются диапазон порта, положительный
таймаут и кэш не агрессивнее самого ESI.

Отдельно про две проверки, которые могут показаться придирками. `DEBUG=True`
в проде — это выполнение произвольного кода через браузер, а не просто подробные
ошибки. SQLite в проде отвергается потому, что сборщик цен пишет из отдельного
процесса одновременно с веб-приложением, и такую запись SQLite не выдерживает.

## База данных

С версии 0.1.0 приложению нужна база: в ней будут жить собранные цены и настройки
вошедших пользователей. В dev это SQLite-файл в `var/`, он создаётся сам. В prod —
MariaDB, MySQL или Postgres, адрес приходит в `DATABASE_URL`.

Схема одна на все четыре СУБД, различия берёт на себя SQLAlchemy. Меняется схема
только миграциями Alembic — руками таблицы не правят.

Накатить схему:

```bash
alembic upgrade head
```

На проде то же самое с профилем:

```bash
APP_ENV=prod alembic upgrade head
```

Адрес базы Alembic берёт из конфигурации приложения, а не из `alembic.ini`: две
записи одного адреса рано или поздно разъезжаются. Строка `sqlalchemy.url` в
`alembic.ini` намеренно пустая.

Примеры адресов:

```
postgresql+psycopg://user:password@localhost:5432/evegas
mysql+pymysql://user:password@localhost:3306/evegas
```

Откат последней миграции — `alembic downgrade -1`, полный откат — `alembic downgrade base`.

## Вход через EVE SSO

Вход нужен ровно для одного: хранить настройки расчёта на сервере, чтобы они
переезжали между браузерами и машинами. **Без входа работает всё** — расчёт,
цены, предупреждения; настройки в этом случае живут в `localStorage`. Если
переменные ниже не заданы, ссылки на вход просто нет, и приложение считает
как считало.

Приложение запрашивает **пустой список scope**: ни кошелька, ни навыков, ни
ассетов. Из токена берутся только идентификатор и имя персонажа.
Refresh-токен не сохраняется.

Настройка:

1. Завести приложение на <https://developers.eveonline.com/applications>,
   тип — `Authentication Only` (scope не нужны).
2. Указать там колбэк. Для разработки `http://localhost:5000/sso/callback`,
   для прода — свой домен по https. CCP сверяет адрес посимвольно: лишний
   слэш в конце уже другой адрес.
3. Положить `ESI_CLIENT_ID`, `ESI_CLIENT_SECRET` и `SSO_REDIRECT_URI`
   в окружение (на своей машине можно в `config.py`).
4. Задать `SECRET_KEY` — им подписывается кука сессии. В dev он генерируется
   на один запуск, и после перезапуска вход придётся повторить.

Заданный только наполовину SSO роняет запуск: один ключ без второго или ключи
без колбэка означают, что вход всё равно не заработает, и молчать об этом хуже,
чем не стартовать.

В профиле prod кука сессии выставляется `Secure`, `HttpOnly` и `SameSite=Lax`,
то есть по открытому http вход работать не будет — это намеренно.

## Сбор цен по расписанию

Приложение **не ходит в ESI по действию пользователя**. Цены собирает отдельная
задача, запускаемая системным cron, а веб-часть читает готовые срезы из базы.
Так нагрузка на ESI не зависит от числа пользователей: сто человек, жмущих
«обновить», — верный путь к бану от CCP.

Один запуск:

```bash
python -m app.jobs.collect
```

Полный обход это 27 газов × 2 формы × 5 хабов = **270 запросов**, около 40 секунд.
По бюджету токенов ESI — 540 из 12 000 за пятнадцатиминутное окно, то есть 4.5%.
Расчёт целиком в [docs/ESI.md](docs/ESI.md).

Запросов на деле меньше: срез не запрашивается, пока не истёк его `expires`,
а повторный запрос уходит с `If-None-Match` и часто получает `304` — он вдвое
дешевле по токенам.

### Расписание

Раз в 30 минут. Чаще смысла нет: ESI кэширует ответ на 5 минут, и обход кэша
CCP прямо называет поводом для бана.

Linux, `crontab -e`:

```bash
*/30 * * * * cd /srv/EveGAS_calc && APP_ENV=prod .venv/bin/python -m app.jobs.collect >> var/collect.log 2>&1
```

Секреты лучше не писать в строку cron: держи их в файле окружения и подключай
через `env $(cat /etc/evegas.env | xargs)` либо задай в самом crontab отдельными
строками `DATABASE_URL=...` до расписания.

Windows, Планировщик задач:

```bash
schtasks /create /tn EveGAS-collect /sc minute /mo 30 /st 00:00 /tr "cmd /c cd /d C:\path\to\EveGAS_calc && .venv\Scripts\python.exe -m app.jobs.collect >> var\collect.log 2>&1"
```

Переход в каталог проекта обязателен, и это не украшение. Планировщик
запускает задачу из `%windir%\system32`, а `python -m app.jobs.collect` ищет
пакет `app` в текущем каталоге — без `cd` задача падает с
`ModuleNotFoundError: No module named 'app'`. В интерфейсе Планировщика тот же
смысл у поля «Рабочая папка».

Проверить, что задача заведена и когда отработает:

```bash
schtasks /query /tn EveGAS-collect /v /fo list
```

### Коды возврата

Чтобы cron и мониторинг понимали, что случилось:

| Код | Значение |
|---|---|
| 0 | всё собрано |
| 1 | часть данных не получена, остальное записано |
| 2 | цикл прерван: ESI ограничил частоту либо сбор уже идёт |

Наложения запусков не будет: задача берёт файловую блокировку `var/collect.lock`
и второй экземпляр сразу выходит с кодом 2. Если процесс умер, не убрав файл,
блокировка считается протухшей через час и подхватывается сама.

### Флаги для отладки

```bash
python -m app.jobs.collect --dry-run --only-hub jita --only-gas fullerite_c320 --verbose
```

`--dry-run` ходит в ESI, но ничего не пишет. `--only-hub` и `--only-gas` сужают
обход до одной пары. `--no-prune` оставляет старые срезы на месте.

### Проверка состояния

```bash
curl http://127.0.0.1:5000/healthz
```

Отдаёт профиль, доступность базы, время последнего успешного сбора и возраст
данных. Код 503 означает, что база недоступна или цены устарели, — это то,
на что стоит натравить мониторинг после развёртывания.

## Запуск

Локально:

```bash
python run.py
```

На хостинге — через waitress, встроенный сервер Flask для продакшена не годится:

```bash
APP_ENV=prod waitress-serve --host=0.0.0.0 --port=8080 --threads=8 --call app:create_app
```

`--call` нужен потому, что `create_app` — фабрика, а не готовый объект приложения.
Потоки нужны, чтобы запросы не выстраивались в очередь за чтением из базы
и отрисовкой шаблона. В ESI веб-процесс не ходит вовсе — этим занят сборщик
по расписанию, и никакого кэша ESI в памяти приложения больше нет.

Полноценное развёртывание — СУБД, nginx, cron, секреты в окружении — отдельная
задача, она в `docs/ROADMAP.md` в разделе «Отложено». Пока проект живёт локально.

Ни Docker, ни Node.js не нужны.

## Как пользоваться

1. Выбери газ и укажи, сколько сырых юнитов нужно.
2. Задай тип структуры и уровень навыка Gas Decompression Efficiency — от них зависит,
   сколько газа переживёт разжатие.
3. Заполни ставки курьерской доставки в ISK за м³ **отдельно для каждого хаба** —
   маршруты разные, и это сильно влияет на результат.
4. Цены уже подставлены из базы приглушённым шрифтом. Любую можно перебить вручную —
   ручной ввод главнее, и при смене объёма сервер такую ячейку не трогает.
5. Смотри таблицу. Верхняя строка — лучший вариант на сейчас.

Таблица пересчитывается сама при изменении любого поля; кнопка «Посчитать» тоже
работает. Галочка «только sell» убирает buy-сценарии: buy-ордер — это заявка,
она может не исполниться, и когда газ нужен сегодня, половина строк только мешает.

Настройки сохраняются сами. Анонимно — в этом браузере, после входа через
EVE SSO — на сервере, вместе с ставками доставки. При первом входе страница
предложит забрать то, что накопилось в браузере.

## Ограничения

- **Рынки игровых структур не видны.** Ордера из Upwell-структур не попадают в публичную
  выдачу API. Если рядом с хабом стоит торговый Keepstar с газом, калькулятор его не учтёт.
- **Цены buy могут быть занижены.** Не учитываются buy-ордера с радиусом действия
  в прыжках, выставленные в соседних системах. Учитываются региональные ордера
  и ордера из системы самого хаба.
- **Курьерка считается по одной ставке за м³.** Лимит объёма на один контракт
  не моделируется — если объём большой, контрактов физически потребуется несколько.
- **Цена — не лучший ордер, а средневзвешенная на нужный объём.** Минимальный sell может
  быть на десяток юнитов при потребности в десятки тысяч. Если стакана не хватило,
  строка результата помечается и показывает, сколько юнитов там на самом деле.
- **Цены не «живые».** Их собирает задача по расписанию, раз в 30 минут; на экране
  всегда написано, сколько данным лет. Если сбор не отработал, сетка помечается
  как устаревшая, а не показывает вчерашние цены молча.
- **Хаб без данных остаётся пустым.** Ноль вместо цены был бы враньём, поэтому
  такие строки просто не участвуют в расчёте, а под сеткой перечислено, каких
  хабов не хватает.
- **Если база недоступна, расчёт по ручным ценам продолжает работать.** Об этом
  пишется прямо под сеткой.
- **`ESI_COMPATIBILITY_DATE` не должна быть в будущем.** ESI считает текущий день
  по UTC-11 и на завтрашнюю дату отвечает `400`. Подробности — `docs/ESI.md` §2.

## Версия

Текущая — **0.1.0**. Номер записан в одном месте, `app/version.py`, и оттуда
попадает и в `app.__version__`, и в User-Agent для ESI.

**Номер двигает только новый функционал.** Исправления, рефакторинг и правки
документации версию не меняют: иначе номер перестаёт что-либо означать
и превращается в счётчик коммитов.

Что было в версиях:

| Версия | Что появилось |
|---|---|
| `0.0.x` | расчёт, интерфейс, чтение цен из ESI по действию пользователя. Ни базы, ни аккаунтов |
| `0.1.0` | база данных и миграции, сбор цен по расписанию, вход через EVE SSO и настройки на сервере |

В `ESI_USER_AGENT` номер писать руками не нужно — на месте `{version}`
подставится текущий. Записанный вручную номер приложение заметит при старте
и предупредит, что он отстал.

## Обновление справочника газов

`data/gases.json` **генерируется** скриптом `tools/build_gases.py` из SDE. Вручную
его не правят: соответствие сжатого типа сырому берётся из `typeMaterials`
(у сжатого газа ровно один материал в количестве 1 — это и есть сырой газ).

Обновлять нужно, только если CCP добавит или переименует типы газа. В рантайме SDE
не используется, зависимостей у скрипта нет — хватает стандартной библиотеки.

```bash
curl -O https://eve-static-data-export.s3-eu-west-1.amazonaws.com/tranquility/sde.zip
```

```bash
python tools/build_gases.py --sde sde.zip --check
```

`--check` ничего не пишет и только показывает расхождения с текущим справочником.
Убедившись, что расхождения ожидаемые, запусти без него:

```bash
python tools/build_gases.py --sde sde.zip
```

Архив (около 107 МБ) распаковывать не нужно, можно указать и путь к распакованному
каталогу. Порядок газов в файле сохраняется, новые типы дописываются в конец.
Любое несоответствие — объёмы не 10:1, не один материал, тип не из группы газов —
это ошибка: скрипт падает и файл не переписывает. После обновления прогони тесты.
